# 실기기 검증 — 알림과 이메일

푸시 알림과 인증 이메일이 **운영에서 한 번도 실행된 적이 없다**는 사실에서 출발한다.
2026-09-30 기준 운영 `PushSubscription` 은 **0건**이었다. 화면은 "알림을 켜세요"라고 말하고
있었지만, 켜진 사람이 없었다.

코드는 통과한다. 테스트도 통과한다. 그래도 **보내는 쪽을 한 번도 실행하지 않았다**는 것은
테스트가 대신할 수 없다 — 브라우저·기기·운영 자격 증명이 다 관여하기 때문이다.

이 문서는 그 부분을 사람과 기기로 확인하는 절차다.

## 먼저 확인 — 세 가지

```bash
npm run notify:check          # 설정이 발송 가능한 상태인가
npm run push:subs             # 구독 표가 비어 있는가 (켜기 전이어야 정상)
```

운영을 보려면 주소를 명시한다. 기본은 언제나 로컬 개발 DB다.

```bash
DIRECT_URL=<운영 주소> npm run notify:check
DIRECT_URL=<운영 주소> npm run push:subs
```

세 가지를 미리 봐야 하는 이유 — **실패했을 때 어디를 봐야 하는지 알 수 없기 때문**이다.
브라우저가 문제인지, 키가 문제인지, DB 가 문제인지는 이 두 명령이 갈라준다.

## 시험이 볼 것 — 사람이 말하는 것으로는 부족하다

"알림이 왔어요" 는 증거가 아니다. **구독 표가 그 사실의 증인**이므로 각 단계 뒤에
`npm run push:subs` 를 돌려 기록한다.

주소는 통째로 찍지 않는다(브라우저 안의 자격 증명이라 지문 8글자로 줄여서 보여 준다).
같은 기기인지 다른 기기인지만 알면 충분하다.

## 준비물

- **같은 계정으로 로그인한 기기 두 대.** 한 대로는 "이 기기만 껐는데 다른 기기가 계속 받는지"
  를 볼 수 없다. 이게 이 시험의 핵심이므로 **두 대가 반드시 있어야 한다.**
- 타이머 알림을 발생시킬 수 있는 시간(회의 제안, 기여도 정정 알림 등)
- **아이폰은 "홈 화면에 추가한 앱"** 상태. 브라우저 탭으로는iphone 푸시가 조용히 실패한다.

## 1단계 — 한 기기 켜기

| | |
|---|---|
| **할 일** | 기기 A 에서 알림함 → 푸시 켜기 |
| **볼 것** | 화면이 "켜짐" 으로 바뀌는가 |
| **증인** | `npm run push:subs` 에 **A 의 기기 지문 1줄**이 잡힌다 |

거기서 멈추면 안 된다. **아직 발송을 확인하지 않았다.** 켜는 것은 저장까지이고, 보내는 것은
별개다.

## 2단계 — 실제로 받는가 (처음 proving)

| | |
|---|---|
| **할 일** | 팀에서 알림이 생기는 일을 한 번 일으킨다(회의 제안·기여도 정정 등) |
| **볼 것** | 앱을 **열지 않고** 알림이 도착하는가 |
| **증인** | 도착했는지 여부 — **여기까지가 표에 안 남는다** |

**2단계가 이번 계획에서 가장 약한 자리다.** 발신 성공/실패의 흔적은 발신 로그에만 있다
(2026-09-30 기준 저장되는 것이 없다). 그래서:

- 안 오면 **서버 함수의 로그를 먼저 본다.** 화면으로는 "켜짐" 이지만 오지 않는 경우가 정확히
  "키는 맞는데 발송이 실패" 다.
- **오면 3단계로 간다.** 그리고 **오지 않았던 기록을 남긴다** — 그 다음 사람이 같은 것을
  다시 헤맨다.

## 3단계 — 클릭하면 앱 안으로 간다

| | |
|---|---|
| **할 일** | 알림을 누른다 |
| **볼 것** | 앱 **밖**으로 나가지 않고 앱 안 경로로 이동하는가 |

`pushPayload` 는 `http` 절대주소와 `//` 스킴 상대주소를 버린다. 브라우저 탭으로 옮겨갈 수
없게 막는 곳이므로, 여기서 깨지면 **알림이 "도착했는데 위험해 보인다"** 가 된다.

## 4단계 — 한 기기만 끈다 ← 오늘 고친 것

| | |
|---|---|
| **할 일** | 기기 B 를 켠 뒤, **기기 A 에서만** 끈다 |
| **볼 것** | A 는 꺼짐으로 뜨고, **B 에는 알림이 계속 온다** |
| **증인** | 끄기 **전** `push:subs` 에 두 줄, **후** 에 한 줄 남고 그 줄이 **B 의 지문**이다 |

**이게 이 시험의 핵심이다.** 예전에는 `deleteMany({ memberId })` 라서 A 를 끄면 **B 까지
사라졌다** — 화면은 "껐습니다"라고 말하고 실제로는 두 기기가 모두 조용히 죽었다. 이 단계가
통과하지 않으면 **3단계까지의 성공은 전부 기기 하나 덕분**이며, 사용자가 처음 끄는 순간
전부 잃는다.

## 5단계 — 죽은 구독은 치워지는가

| | |
|---|---|
| **할 일** | 브라우저 개발도구에서 구독을 지운다(로그아웃/데이터 삭제). 서버에는 행이 남는다 |
| **볼 것** | 404/410 이 나면 그 행이 사라지는가 |
| **증인** | `push:subs` 의 그 줄이 사라진다 |

지워질 것은 404·410 뿐이다. 401·403 은 **우리 쪽 서명이 잘못됐다는 뜻**이라 지우면 정상인
기기들을 설정 실수 한 번으로 전부 지우는 셈이 된다. 이 구분은
`pushFailure()` 가 하며, 스모크가 고정한다. 여기서 확인하는 것은 **그 구분이 실제로
동작한다** 는 것이다.

## 6단계 — 다시 켜도 되돌아간다

| | |
|---|---|
| **할 일** | 5단계에서 지워진 기기로 다시 켠다 |
| **볼 것** | 새 구독이 저장되고 알림이 오기 시작하는가 |

## 7단계 — 인증 이메일 (운영 Gmail 이 처음 도는 것)

운영에는 `RESEND_API_KEY` 가 없고 **`GMAIL_USER` · `GMAIL_APP_PASSWORD` 만** 있다. 이 경로는
운영에서 **한 번도 실행되지 않았다.**

| | |
|---|---|
| **할 일** | 실제 이메일 주소로 인증을 요청한다 |
| **볼 것** | **도착**하는가, 링크가 어디로 가나 |
| **증인** | 링크가 `http://localhost:3000` 이면 **실패다** |

운영 링크는 `VERCEL_PROJECT_PRODUCTION_URL` 로 자동으로 잡힌다(2026-09-30 확인함).
`APP_URL` 이 없어도 정상이다. 그런데 **실제로 도착한 링크의 주소를 눈으로 봐야 한다** —
코드가 그렇게 짜져 있다는 것과 그 주소가 클릭되는 것은 다른 일이다.

운영 로그에 **인증번호가 남지 않는지**도 함께 본다. 그게 이 경로의 목적이기도 하다.

## 8단계 — 아이폰

아이폰은 **홈 화면에 추가한 앱**에서만 확인한다. 브라우저 탭으로는 알림 권한을 물어도
granted 가 되지 않고 **조용히 실패**한다. 상태 표시가 "설치하세요" 라고 말하는 것이 그 때문이다.

| | |
|---|---|
| **할 일** | 홈 화면에 추가한 뒤 앱에서 켜기 |
| **볼 것** | 켜짐으로 뜨고, 알림이 도착하는가 |

## 끝나고 남길 것

각 단계의 결과를 **여기 아래**에 적는다. 실패한 것은 실패한 것으로 남기는 것이 이번 계획의
목적이다 — 통과시킨 것처럼 적어 두면 다음 사람이 같은 것을 다시 헤맨다.
