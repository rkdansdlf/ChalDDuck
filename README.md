# 찰떡 (ChalDduck)

대학생 팀 프로젝트(팀플)를 위한 협업 앱. **초대 링크 + 이름**으로 들어와서 역할을 조율하고,
회의 시간을 잡고, 자료를 모으고, 기여 기록을 남깁니다.

계정 가입은 없습니다 — **이메일을 쓰는 것은 이미 팀에 속한 사람이 몇 팀 중 어디로 들어갈지
고르는 보조 길**일 뿐입니다(1-2절).

디자인 핸드오프(33화면 프로토타입)를 실제 코드베이스로 옮기는 중입니다.

## 스택

| | |
|---|---|
| 프레임워크 | Next.js 16 (App Router) · React 19 · TypeScript |
| 스타일 | Tailwind CSS v4 + CSS 변수 디자인 토큰 |
| 아이콘 | lucide-react (직접 등록한 것만 번들에 들어감) |
| 서체 | Pretendard Variable (저장소에 포함, `next/font/local`) |
| 데이터 | PostgreSQL (Supabase) + Prisma |
| AI | OpenRouter (기본 `openrouter/free`) |
| 서버 | Next.js Server Actions |

### 처음 실행

```bash
npm install
```

`.env` 를 만들고 Supabase 대시보드 > Connect 의 값으로 채웁니다
(`.env.example` 참고 — 커밋되지 않습니다).

#### 로컬 DB 로 개발하기 (권장)

`.env` 는 **운영(배포본)과 같은 Supabase** 를 가리킵니다. 개발 중에 누르는 버튼이
실제 팀의 데이터를 바꾸지 않도록, 로컬 Postgres 를 따로 두고 `.env.development.local` 로
덮어씁니다(커밋되지 않습니다).

```bash
createdb chalddeok_dev               # Homebrew Postgres 기준
```

```bash
# .env.development.local
DATABASE_URL="postgresql://<사용자>@localhost:5432/chalddeok_dev"
DIRECT_URL="postgresql://<사용자>@localhost:5432/chalddeok_dev"
SUPABASE_URL=""                      # 파일 저장소를 끈다 — 운영 버킷에 쌓이지 않게
```

```bash
npx prisma migrate deploy            # 표 만들기
npm run db:seed                      # 데모 팀 한 개 넣기
npm run dev
```

이 파일은 `next dev` 뿐 아니라 **Prisma CLI 와 시드도 먼저 읽습니다**
([`scripts/load-env.mjs`](scripts/load-env.mjs)). 그래서 파일이 있는 동안에는
`prisma migrate` 가 운영 DB 로 가지 않습니다. 운영에 직접 마이그레이션해야 할 때만
잠시 치우세요(평소에는 배포가 `prisma migrate deploy` 를 돌립니다).

시드는 로컬이 아닌 DB 를 가리키면 멈춥니다(같은 초대 코드의 팀을 지우고 다시 넣기
때문입니다). 정말 원격에 넣으려면 `ALLOW_REMOTE_SEED=1` 을 붙입니다.

로컬 시드에는 데모 팀원 네 명이 같은 재입장 코드를 받습니다 — `/join/rejoin` 에서
초대 코드 `CD3-7F2Q`, 이름(김민준·이서연·박지호·최유나), 재입장 코드 `DEMO-DEMO-DEMO`.
원격에 넣을 때는 코드를 넣지 않습니다(누구나 아는 코드는 뒷문이 됩니다).

`DATABASE_URL` 은 런타임용 **트랜잭션 풀러(6543)**, `DIRECT_URL` 은 마이그레이션·시드용
**직결(5432)** 입니다. 풀러로는 prepared statement 와 DDL 잠금을 못 버텨 마이그레이션이 깨집니다.

런타임 커넥션 풀은 [`src/server/db.ts`](src/server/db.ts) 에서 직접 만듭니다 — 쉬고 있던
연결이 끊겼을 때 프로세스가 죽지 않게 받아 주고, 순간적인 연결 실패(P1001·P2024)는
짧게 두 번 다시 시도합니다. 자세한 이유는 그 파일 주석에 있습니다.

## 반응형

| 폭 | 레이아웃 |
|---|---|
| ~599px | 뷰포트를 꽉 채우고 **하단 5탭**으로 이동 |
| 600~1023px | 본문이 860px 까지만 넓어지고 가운데 정렬 · 하단 탭바 유지 |
| 1024px~ | 탭바가 **왼쪽 세로 막대**로 바뀌고 본문에 폭을 내줌 |

폭이 생기면 화면도 그에 맞게 바뀝니다 — 홈은 두 기둥, 드라이브 제출함은 두 줄,
기여도 리포트는 A4 비율, 08 시간표 격자는 칸이 44px 로 커져 최소 탭 영역을 지킵니다.

온보딩은 탭이 없는 집중 흐름이라 넓은 화면에서도 420px 카드로 모읍니다 —
입력칸 하나가 화면 폭만큼 늘어나면 읽기 어렵습니다.

**채팅(33번)은 넓은 화면에서 실제로 3분할로 동작합니다.**

| 폭 | 채팅 |
|---|---|
| ~1023px | 화면을 한 번에 하나씩 (32 → 19 / 31) |
| 1024px~ | 목록 + 대화 |
| 1280px~ | 목록 + 대화 + 자료·정보 |

1024px 에서 세 기둥을 다 펴지 않는 이유는 왼쪽 앱 내비게이션이 232px 을 이미 쓰기 때문입니다 —
거기서 세 기둥을 펴면 대화 칸이 말풍선 한 줄도 못 담습니다.

## 검토 모드

기획안에 규칙이 없어 임시로 정한 지점은 화면 안에 `[검토]` 점선 박스로 표시돼 있고,
**평소에는 보이지 않습니다.** 확인하려면 URL 에 `?review=1` 을 붙이거나 콘솔에서 `__CD_REVIEW__()`.

확정이 필요한 지점의 목록은 **여기에 적지 않습니다** — 화면이 곧 목록이고, 위의 방법으로
한 번에 다 볼 수 있습니다. 문서에 개수를 적어 두면 화면이 늘었는데 숫자를 고치지 않는 일이
반복됩니다. 원래 기획안과 주고받은 기록은 [`docs/handoff/HANDOFF.md`](docs/handoff/HANDOFF.md)
에 남아 있습니다(역사 문서이므로 지금의 목록과 다를 수 있습니다).

## 검사

```bash
npm run verify
```

`db:check` 는 **지금 가리키는 DB** 와 스키마를 비교합니다. 로컬에서 돌리면 로컬 DB(에셋)를
봅니다 — "마이그레이션을 깜빡했나"를 잡는 검사입니다. **"운영 DB 가 뒤처졌나"를 잡는
것은 Vercel 빌드 쪽** `db:check` 입니다(거기서는 `DIRECT_URL` 이 운영 DB 를 가리킵니다).
두 개를 같은 이름으로 부르는 이유가 있어 헷갈리기 쉬우니 기억해 두세요.

### 푸시 전에 자동으로

```bash
cp scripts/pre-push.sh .git/hooks/pre-push && chmod +x .git/hooks/pre-push
```

`verify` 를 돌립니다 — Vercel 이 하는 배포 게이트를 **더 엄격하게** 로컬에서 합니다. 순서가
꼭 같을 필요는 없습니다. Vercel 에만 있는 것도, 로컬에만 있는 것도 있습니다.

| | 로컬 (`npm run verify`) | Vercel (`vercel.json`) |
|---|---|---|
| `prisma migrate deploy` | — | **한다.** 운영 DB 에 실제로 적용한다 |
| `db:check` · `storage:check:gate` · 빌드 | 한다 | 한다 |
| `db:migrations` | **한다** | — |
| `test` · `tsc` · `lint` | **한다** | — |

로컬에만 있는 세 개는 각자의 이유가 있습니다. `db:migrations` 은 "파일이 커밋됐는가"인데
Vercel clone 은 커밋된 것만 받아서 **항상 통과합니다.** `test`·`tsc`·`lint` 는 시간을 산다 —
배포를 막을 이유가 아니라면 CI 에서 돌립니다. 반대로 Vercel 만 하는 `migrate deploy` 는
로컬에서 대신할 수 없고, **빌드는 죽었는데 마이그레이션은 이미 운영 DB 에 적용된** 상태로
남을 수 있습니다(그래서 실패한 배포 뒤에는 롤백이 아니라 코드를 굴립니다).

2026-09-28 에 화면만 먼저 반영하고 `src/data/api.ts` 반영을 빼서 **타입 에러 57건**인 커밋이
push 돼 Vercel 빌드가 두 번 실패했습니다. 그 사실을 알게 된 건 배포 목록을 봤을 때뿐이었고,
로컬에서 먼저 멈추게 하는 것이 그 일을 막습니다.

`.git/hooks/` 는 커밋되지 않으니 **규칙은 [`scripts/pre-push.sh`](scripts/pre-push.sh) 에
있습니다.** 위 줄은 그 파일을 부르는 것만 합니다. 빼고 싶으면 `--no-verify` 로 부르되, 그
뒤 Vercel 이 빨개질 수 있다는 것을 알고 하세요.

### 역할 추첨 검사

```bash
npm run test:roles
```

여섯 액션이 전부 미검증이었다(`npm run audit:actions` 기준 "없음"). 그런데 규칙이 **"라이어 제시어
목록은 임시로 정했습니다" 와 같은 자리**에 있는 종류다 — 팀이 동의해야 하는데 몇 명을 모으는지 세는
곳이다.

검사 42건 — 제안하면 팀에 **알림이 간다**(없으면 마감만 지나가고 아무도 모른다) · **같은 역할에 두
번 제안할 수 없다** · 동의는 중복돼도 한 줄이고 **반대는 제안을 지운다**(그리고 팀에 알림) ·
**동의가 살아 있으면 뽑지 않는다** · **도구는 팀이 동의한 것을 쓴다** — 눌러서 임의의 도구로 바꾸면
팀이 동의한 대상이 아니게 된다 · 결과는 **당사자가 받을 때까지** 확정되지 않는다 · **확정된 뒤에는 다시
뽑을 수 없다** · 무효 추첨(당첨자가 나감)만 자리를 비운다 · 당사자가 **거절하면 결과가 지워지고** 다시 비운다 · **남이 대신 거절할 수 없다** · **이미 확정한 것은 거절로 뒤집지 않는다**(경쟁 상태가 되지 않는다) · **혼자 인 경우에만** 그 역할을 맡고(`claimSoleRole`) 도구는 `"담당"` · **겹치거나 아무도 안 골랐으면** 못 맡는다.

**세 가지를 재서 적었다**
- **동의한 사람 수는 관계없다.** `awaitingConsent` 는 **마감 시각만** 본다 — 전원이 동의해도 마감 전이면
  뽑을 수 없다. 그리고 **동의가 강제되지 않는다** — 마감 뒤에는 동의 없이도 뽑힌다.
- **추첨 성공은 `"drawn"` 이 아니라 `"ok"` 다.** 그리고 **뽑으려면 하고 싶은 역할이 있어야 한다** —
  후보가 없으면 `empty` 로 끝나고 **뽑힌 것이 아니다.**
- **확정된 결과의 거절 거부는 지금은 두 겹이다.** 앞선 `myPendingDraw` 이 확정분을 먼저
  거절하고(`"gone"`), 그 아래 `deleteMany` 의 `accepted: false` 는 **도달하지 않는다.** 하네스로는
  **뒤의 줄을 끊어도 깨지지 않는다** — 앞에서 이미 막기 때문이다. 앞단을 고쳐야 드러난다.
  두 겹인 것은 의도고, 남는 이유를 코드에 적어 두었다.
- **`as(팀.멤버)` 와 `as(팀.세션토큰)` 을 헷갈리면 서버가 엉뚱한 말을 한다.** 멤버 객체를 넘기면
  Prisma 가 `token` 이 객체라며 던지고 그 아래의 진짜 이유를 가린다. 하네스가 **토큰이 문자열인지
  먼저 보고** 막는다 — 그랬어야 "로그인이 필요합니다" 라는 엉뚱한 말 대신 맞는 말을 하게 된다.

**검사가 규칙을 실제로 본다** — 동의 확인과 도구 규칙을 무시하면 두 건이 깨진다.

### 재입장 검사

```bash
npm run test:rejoin
```

재입장은 오늘 우리가 직접 고친 자리가 세 곳이다 — 동명이인 · 기기 끄기 · 재입장 코드. 그런데
**`rejoin.ts` 의 여섯 액션은 아무도 부르지 않았다.**

가장 위험한 곳은 **코드 찍기와 잠금**이고, 주석에 이런 사고가 적혀 있다 —
"팀 코드와 이름 아무 쌍이나 알고 있는 사람이 그 쌍을 10분씩 잠글 수 있었다". **고쳐졌다는 것을
아무도 확인하지 않았다.**

검사 22건 — **없는 사람(팀 코드+이름)은 실패로 세지 않는다**(그 쌍을 아는 사람이 아무 코드나 찍어도
**누구도 잠기지 않는다**) · 코드를 아직 받지 못한 사람도 세지 않는다 · **틀린 코드는 세고 6회째에
잠긴다** · **맞는 코드도 잠기면 못 들어간다** · 잠금은 **(팀 코드, 이름) 조합 단위**다 · 맞으면
카운터가 비고 · 나간 사람이 돌아오면 명단에 돌아온다 · **코드를 새로 만들면 이전 코드는 즉시 못 쓴다** ·
**기기를 지우는 것은 내 것만**.

**잠기는 시점은 재서 적었다** — 한계가 10분에 5회이고 판정이 `> max` 이므로 6회째로 짐작했는데,
**재보니 6회째였다**(주석으로 짐작하지 않는다 — 내가 짐작했다가 틀릴 뻔했다).

**카운터 키는 sha256 해시다** — 팀 코드로 `contains` 로 찾으려고 하면 **영원히 0 이 나온다**(내가
그랬다). 코드의 키 계산을 그대로 불러와야 **무엇을 세는지**를 볼 수 있다.

⚠️ **남는 위험 하나를 고치지 않고 고정한다** — 잠금의 키가 `(팀 코드, 이름)` 이므로 **그 조합을 아는
사람은 그 팀원을 10분 잠글 수 있다.** "없는 사람은 세지 않는다" 는 고정이 **그 조합을 이미 아는
사람에게는 도움이 되지 않는다.** 팀 코드와 이름은 화면에 보이기 때문이다. 고치는 대신 여기서
고정한다 — 다음 사람이 이 결정을 낼 때 근거가 눈앞에 있어야 한다.

하루에 한 번 도는 주소가 **하나** 있고, 그 주소가 사용자 화면의 네 문장을 참으로 만듭니다.

**지금은 하나가 던져도 나머지가 돈다.** 회의 확정이든 기록 청소든 **서로 무관한 일**이므로
`Promise.allSettled` 로 따로 돌리고, **무엇이 실패했는지 응답으로 말한다**(`failures`). 조용히
0 을 말하지 않는다 — **0 과 실패는 전혀 다른 말**이다. 이 흉내를 내어 확인했다(회의 확정을 흉내
내고 청소 하나를 흉내 내면 `failures: ["confirmed","attempts"]` 가 나온다).

이 검사는 그 주소를 **직접 부른다.** cron 은 요청 밖에서 부르면 `revalidatePath` 가 던지는 구조라
**직접 부르는 것 자체가 불가능**했는데, 하네스의 `next/cache` 스텁이 그 자리를 통과시킨다 —
경계 안에서 도는 것과 같은 코드가 돌아가고, 무엇을 알렸는지도 기록으로 남는다.

**검사가 스스로를 구별하지 못하는 문제를 이 자리에서 또 잡았다.** 처음엔 경계를
`AI_POLICY.retentionDays` 에서 읽었다. 그랬더니 **보관 기간을 36500일로 바꿔도 통과했다** —
기대값이 같은 상수에서 나오니 검사도 따라갔다. 화면이 "90일 뒤" 라고 말하는 동안 100년을 말하게
되는 검사는 아무것도 확인하지 않는다. 그래서 **화면이 말하는 숫자(90)** 를 코드에 적고, 정책과
화면이 같은지 따로 확인한다.

**액션이 스스로 막는지**를 본다(화면이 버튼을 숨겼다고 안전하지 않으므로).

2GB 를 실제로 올릴 수는 없다. 그래서 **큰 버전을 DB 에 심는다** — 팀 사용량은 저장소가 아니라
`FileVersion.bytes` 의 합이라 심은 만큼이 실제로 한도 직전·직후가 된다. 올리는 대상은 진짜
저장소 객체다(몇 KB).

⚠️ **로컬 DB 와 개발 버킷에서만 돕다.** 팀을 만들고 저장소에 올렸다가 지우기 때문에,
운영 DB 나 운영 버킷(`submissions`) 을 가리키는 채로 한 번 돌면 팀이 남는다. 진입점이 두
가지를 확인하고 멈춘다(`scripts/harness/drive.mts`).

**이 검사가 실제로 버그를 하나 잡았다(2026-09-28).** 팀이 꽉 찬 뒤에 화면이 같은 응답을 다시
보내면 `over-quota` 로 돌아갔고, 거절된 올리기의 정리(`storage().remove`)가 **이미 기록된
객체를 지웠다.** 업로드는 성공했는데 파일이 사라지고 버전 행만 남았다. 원인은 잠금 안에서
**중복 응답 검사가 용량 검사 뒤에 있었던 순서**였고, 순서를 바로잡았다(`server/actions/drive.ts`).

하네스 자체가 서 있는지 따로 본다 — 세션 없는 호출이 실제로 막히는가:

```bash
npm run test:drive:probe
```

### 저장소 자가진단

```bash
npm run storage:check
```

스키마가 아니라 **버킷**을 봅니다 — 환경변수·버킷 존재·비공개·50MB 제한, 그리고 **서명 주소
를 실제로 발급받는지**까지. 버킷이 보여도 키가 틀리면 마지막에서 걸립니다.

이 검사가 필요한 이유가 있습니다. `isStorageConfigured()` 는 환경변수의 **존재만** 봅니다 —
2026-09-28 에 실제로 환경변수는 다 채워져 있는데 **버킷을 한 번도 만들지 않은** Supabase
프로젝트였습니다. 그 상태에서 앱은 "연결됐다"고 말하면서 올리기만 조용히 실패했고, 그때
스키마 검사는 아무것도 잡지 못했습니다(저장소를 만질 일이 없으므로 당연합니다).

## 배포 (Vercel)

**배포돼 있습니다 — https://chalddeok-omega.vercel.app**

저장소가 Vercel 프로젝트(`chalddeok`)에 연결돼 있어 `main` 에 푸시하면 자동으로 배포됩니다.
**배포는 항상 푸시한 커밋에서** 일어납니다 — Vercel 이 `github.com/rkdansdlf/ChalDDuck` 를
그 커밋으로 클론해서 빌드합니다.

#### 배포가 실패했을 때 — 무엇이 원인인가

```bash
npm run deploy:why              # 가장 최근 배포
npm run deploy:why -- <배포 아이디>   # 그 배포
```

`● Error` 만 보고 고치지 마세요. **빌드가 시작했느냐**가 둘을 가릅니다.

| 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| 소요 시간이 **없다** | Vercel 이 **빌드를 시작하지 못했다.** 코드는 실행되지 않았다 | 몇 분 뒤 같은 커밋으로 다시 시도. hobby 는 프로젝트당 동시 빌드가 제한돼 있어 겹친 빌드가 원인인 경우가 많다 |
| 소요 시간이 **있다** (30~60초) | 빌드가 돌았고 **코드**가 실패했다 | `npm run verify` 를 로컬에서 돌린다 |

2026-09-28 에 두 번째 경우가 여러 번 연속(6회) 왔는데 전부 첫 번째였고, 몇 분 뒤 같은
커밋이 그대로 성공했다. Vercel 이 `Resource provisioning failed` 로 빌드 머신 배정을 거부한
것이고, 그 오류는 **빌드 로그가 한 줄도 없어서** CLI 로는 원인을 볼 수 없다 — 그래서 이
도구가 있다.

`npx vercel --prod` 로 직접 올릴 수도 있지만 그러면 **푸시하지 않은 커밋까지 배포**됩니다.
배포본이 `main` 보다 앞서고, 다음 푸시가 또 다른 배포를 만들어 배포 이력이 두 갈래로벌어집니다. 되도록 푸시로만 올리세요.

`vercel.json` 의 `buildCommand` 가 빌드 순서를 정합니다 —
`prisma migrate deploy && npm run db:check && npm run storage:check:gate && npm run build`.
**푸시 = 마이그레이션 적용 + 가드 + 빌드** 이므로 `db:check` 를 빠뜨릴 길이 없습니다.

⚠️ **마지막은 `next build` 가 아니라 `npm run build` 여야 합니다.** `next build` 를 직접 부르면
`package.json` 의 `build` 스크립트를 **통째로 건너뛰고**, 그 안에 있는 플래그가 배포에 닿지
않습니다. 실제로 그랬습니다 — Next 16 은 `next build` 의 기본값이 Turbopack 인데, 이 앱은
`--webpack` 으로 돌아가도록 해 둔 상태였고(`next/dist/docs/01-app/02-guides/upgrading/version-16.md`),
배포는 그 플래그를 못 받아 Turbopack 으로 돌다가 `globals.css` 후처리에 죽었습니다. **로컬
`npm run build` 는 통과하는데 배포만 빨간** — 이 문서를 고쳤어야 그 차이를 읽을 수 있었다는
뜻입니다.

새로 세팅한다면 저장소를 Vercel 프로젝트에 연결하고 **환경변수 여덟 개**를 넣으면 됩니다.

| 변수 | 없으면 |
|---|---|
| `DATABASE_URL` | 앱이 뜨지 않습니다 (런타임 · 트랜잭션 풀러 6543) |
| `DIRECT_URL` | **빌드가 실패합니다** — 마이그레이션이 이걸 씁니다 (직결 5432) |
| `CRON_SECRET` | 회의 마감 예약 작업이 항상 401 입니다 |
| `SUPABASE_URL` + `SUPABASE_SECRET_KEY` | 파일 업로드만 막히고 앱은 돕니다 |
| `OPENROUTER_KEY` | AI 도구가 샘플만 돌려주고 앱은 돕니다 |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` + `VAPID_PRIVATE_KEY` | **푸시가 전혀 나가지 않습니다** — 알림함의 "알림 받기"가 켜지지 않는다고 그대로 말합니다 |
| `GMAIL_USER` + `GMAIL_APP_PASSWORD` | **이메일 로그인이 되지 않습니다** — 발송 실패라고 그대로 말합니다 (무료·도메인 불필요) |
| `RESEND_API_KEY` + `RESEND_FROM` | 위와 같습니다. 단 `RESEND_FROM` 의 도메인은 Resend 에서 인증돼 있어야 합니다 |
| `APP_URL` | 비워도 배포 주소로 자동 채워집니다. 이마저도 없으면 도착한 메일의 매직 링크가 `http://localhost:3000` 을 가리켜 링크를 눌러도 로그인이 되지 않습니다 |

**둘 중 하나만 있으면 됩니다.** 둘 다 있으면 Gmail 을 씁니다. 도메인이 생기면 `GMAIL_*` 를
빼고 `RESEND_*` 만 남기면 됩니다 — 코드 수정이 아니라 환경변수만 바꾸면 되는 구조로 두었습니다.

#### 없어도 되는 변수 — 코드에 기본값이 있습니다

위 표와 달리 이 셋은 **비워도 앱이 돕습니다.** 값을 안 읽으면 코드 안의 기본값을 씁니다
(그래서 배포할 때 넣을 필요가 없습니다).

| 변수 | 비우면 | 기본값 |
|---|---|---|
| `VAPID_SUBJECT` | 푸시가 "알 수 없는 발신자"로 보일 수 있습니다 | `mailto:team@chalddeok.app` (`server/notify/push.ts`) |
| `SUBMISSIONS_BUCKET` | 버킷 이름이 `submissions` 가 됩니다 | `submissions` (`server/storage/client.ts`) |
| `SUPABASE_SERVICE_ROLE_KEY` | `SUPABASE_SECRET_KEY` 를 대신 봅니다 | — (별칭) |

`VAPID_SUBJECT` 는 **발신자로 보이는 연락처**입니다. 웹푸시는 이 값을 못 읽으면 일부 기기에서
"알 수 없는 발신자"로 보입니다 — 앱 안에서는 아무 일도 안 보이는 차이라, 넣지 않으면 이유를
찾을 자리가 없습니다.

`RESEND_API_KEY` 는 **Vercel 의 Supabase 연동으로 채워지지 않습니다.** 연동은 `SUPABASE_*`
만 채워 넣습니다. 그리고 Resend 는 **도메인을 소유해야만** 보낼 수 있는데, `*.vercel.app` 은
Vercel 이 소유한 공유 도메인이라 DNS 를 건드릴 수 없어 인증 자체가 불가능합니다. 그래서
도메인이 없는 동안 Gmail 이 유일한 무료 길입니다.

⚠️ **`GMAIL_APP_PASSWORD` 는 그 주소로 메일을 보낼 권한 그 자체입니다.** Vercel 환경변수는
프로젝트에 접근하는 사람이 볼 수 있으니 공용 발신자로 쓸 계정 하나만 정하세요. Gmail 자동발송
약관상 하루 수십 통 수준은 괜찮지만, 어설프게 쓰면 계정이 잠깁니다.

`RESEND_API_KEY` 와 `APP_URL` 은 이메일 인증(**입장 화면 01**의 보조 경로)에만
쓰입니다. 없는 동안에도 나머지 앱은 그대로 돕습니다 — 다만 **운영에서 인증번호를 화면에 되돌려
주는 도움은 꺼집니다.** 그 값이 새면 메일 발송이 실패해도 인증번호가 도착해 로그인 경로가
우회되기 때문입니다. 로컬 개발(`next dev`)에서만 6자리가 서버 로그와 화면에 보입니다.

푸시 키 쌍은 `npx web-push generate-vapid-keys` 로 한 번만 만듭니다. **배포와 로컬에
같은 값**을 넣어야 합니다 — 서버와 브라우저의 키가 다르면 구독은 만들어지지만 아무것도
오지 않습니다(화면은 "켜짐"이라고 말합니다). 값을 바꾸면 예전에 구독한 기기들이 전부
구독을 다시 해야 합니다.

⚠️ **`.env` 는 배포본과 같은 Supabase 프로젝트입니다.** `.env.development.local` 없이
`npm run dev` 를 띄우면 로컬에서 누른 것이 그대로 실제 팀의 데이터가 됩니다 — 위의
"로컬 DB 로 개발하기"를 먼저 해 두세요.

빌드 명령은 `vercel.json` 에 있습니다 —
`prisma migrate deploy && npm run db:check && npm run storage:check:gate && npm run build`.
**배포할 때마다 마이그레이션이 먼저 돕고, 그다음 DB 가 스키마와 같은지 확인합니다.**

#### `db:check` — 왜 있는가

`prisma migrate deploy` 는 **"할 일이 없다"를 실패로 보지 않습니다.** 그래서
`prisma/schema.prisma` 만 고치고 마이그레이션 파일을 빠뜨려도 배포가 **초록불**입니다.
그렇게 올라간 Prisma 클라이언트는 첫 질의에서 죽고, 죽은 건 서버 컴포넌트라
브라우저에는 `Minified React error #441` 로만 찍힙니다. 실제로 그렇게 배포가 성공하고
`/chat` 이 깨진 적이 있습니다 — 서버 컴포넌트가 예외를 내면 RSC 페이로드의 에러 행으로
바뀌고, 그 행을 클라이언트가 되살린 것이 441 입니다. **진짜 원인은 Vercel 함수
로그에만 있습니다.**

그래서 마이그레이션을 덮은 **직후에** DB 와 스키마를 직접 비교합니다
(`prisma migrate diff`, [`scripts/check-schema-in-sync.mjs`](scripts/check-schema-in-sync.mjs)).
차이가 있으면 **빌드가 실패합니다.** 로컬에서 미리 확인하려면 `npm run db:check`.

규칙 하나만 지키면 됩니다: **`prisma/schema.prisma` 를 건드린 커밋에는 반드시
마이그레이션을 함께 넣는다.** 그래야 `migrate deploy` 가 할 일을 찾습니다.

#### `db:migrations` — 마이그레이션이 커밋되었는지

`db:check` 는 **DB 와 스키마**만 비교합니다. "파일이 생겼는데 커밋 안 됐다"는 그 둘 어디에도
없습니다. 그래서 이런 일이 실제로 났습니다.

1. 읽기 순화 표를 만들며 `prisma migrate dev` 를 돌렸습니다. 파일이 생겼고 로컬 DB 에도,
   실수로 **운영 DB 에도** 적용됐습니다. 그런데 **커밋은 하지 않았습니다.**
2. 푸시했습니다. `migrate deploy` 는 커밋된 것만 보고 "할 것이 없다"고 정상 종료합니다.
3. `ReadCushion` 의 `"on"` 컬럼을 지우는 마이그레이션이 **저장소에 없어서** 실행되지 않아,
   운영 DB 에 그 컬럼이 남았습니다.
4. `db:check` 가 그 차이를 잡아 빌드가 실패했습니다 — 즉 **증상은 잡혔고 원인은 남았습니다.**
   스키마가 더 안 바뀌었다면 조용히 지나갔을 차이입니다.

그래서 **푸시 전에** 이 검사를 둡니다(`npm run db:migrations`, `npm run verify` 의 **두 번째** 단계):

```bash
npm run db:migrations
```

`prisma/migrations` 의 파일이 **커밋된 것(`HEAD`)** 과 같은지 봅니다.
`git ls-files` 가 아니라 `git ls-tree HEAD` 인 이유는 **`git add` 만 하고 커밋을 안 한
상태**를 잡아야 하기 때문입니다 — 스테이징한 파일은 인덱스에는 있어도 푸시엔 가지 않습니다.
커밋돼 있는데 디스크에서 사라진 마이그레이션과, `migration.sql` 이 없는 폴더도 함께 봅니다.

**로컬에서만 도는 것이 맞습니다.** Vercel 은 저장소를 커밋 그대로 클론해서 디스크와 `HEAD` 가
항상 같고, 잡을 수 있는 시점도 이미 지나간 뒤입니다. 이 사고를 만들 수 있는 곳은 **푸시하기
전의 로컬**뿐입니다.

버킷은 한 번만 만들면 됩니다(`npm run db:storage`). **버킷은 Supabase 에만 있습니다** —
로컬 Postgres 에는 `storage` 스키마가 없어 이 명령이 목적을 이루지 못합니다. 그래서
로컬 DB 를 가리키면 아무것도 건드리지 않고 그 사실을 알려주고 끝냅니다.

예전에는 이 명령이 `.env`(운영)만 읽어, `next dev` 는 로컬 DB 를 보는데 **운영 DB 의 버킷을
바꾸러 갔습니다.** 시드가 가진 가드를 붙여 로컬이 아닌 곳을 가리키면 명시적 허락
(`ALLOW_REMOTE_SEED=1`) 없이는 실패하게 했습니다. 버킷을 만들 대상은 직접 지목하세요 —
운영에 만들려면 그쪽 주소를 담은 환경에서 실행하고 `ALLOW_REMOTE_SEED=1` 을 붙입니다.

⚠️ **Vercel Hobby 는 예약 작업이 하루 한 번까지**입니다. `vercel.json` 의 schedule 을
그보다 잦게 적으면 **배포가 실패합니다**. 지금은 하루 한 번(00:00 KST)이고, 화면이
`effectiveStage()` 로 직접 계산하므로 이 작업이 늦어도 사용자는 맞는 상태를 봅니다.

| 메시지 보내기 · 읽음 표시 | `server/actions/chat.ts` |
| AI 도구 호출 자리 | `server/actions/ai.ts` (쿠션·문장 변환은 `/api/ai/stream`) |

온보딩 중에만 쓰는 `features/onboarding/onboarding-state.ts` 는 남겨 뒀습니다 —
아직 팀에 저장되기 전의 선택이라 서버로 보낼 것이 없습니다.

### 1-1. 회의 응답 마감

마감은 시각이 지나면 저절로 오는 일이라 아무도 앱을 열지 않아도 지나갑니다. 두 겹으로 둡니다.

- **화면은 계산해서 보여 줍니다.** `effectiveStage()` 가 "마감이 지났고 반대가 없으면 확정"을
  그 자리에서 판단하므로, 예약 작업이 늦게 돌아도 지나간 마감이 "대기 중"으로 보이지 않습니다.
- **표는 예약 작업이 맞춥니다.** `/api/cron/meetings` 를 주기적으로 부르면 마감이 지난 제안을
  `confirmed` 로 바꿉니다(`vercel.json` 에 **하루 한 번** 등록 — Vercel Hobby 는 그보다
  잦으면 배포가 실패합니다. Pro 이상이면 schedule 만 바꾸면 됩니다). 다른 데 올린다면 어떤
  스케줄러로든 이 주소만 부르면 됩니다. `CRON_SECRET` 이 없으면 **항상 401** 입니다.
  이 작업이 지난 재입장 시도 기록과 보관 기간이 지난 AI 사용 기록도 함께 치웁니다 —
  둘 다 하루 한 번이면 충분하고, 늦어도 틀리지는 않습니다.

마감이 지난 뒤의 반대는 서버가 거절합니다 — 받아 주면 이미 확정된 회의가 뒤집힙니다.
24시간을 기다리지 않고 마감 뒤 화면을 보려면 09 화면의 "마감 지금으로 당기기 (데모)"
버튼을 쓰세요(개발 환경에서만 보입니다). **확정하지 않고 시계만 당기므로** 그 버튼으로 본
화면이 실제 마감 뒤의 화면과 같습니다.

### 1-2. 인증

계정 가입은 없습니다. **팀에 들어오는 모든 길의 마지막 문은 팀장이 엽니다.** 다만 그 문은
예전처럼 팀 전체가 나눠 가진 코드 한 개가 아니라 **초대 한 장**입니다.

코드로 바꾼 이유는 그 코드가 **되돌릴 수 없었기** 때문입니다 — 팀장도 모르게 새 사람이 그
코드로 들어와 팀의 기여 기록과 대화를 볼 수 있었습니다. 초대 한 장을 만들면 **그 공유 하나만**
골라 되돌릴 수 있고, 쓸 횟수와 기한도 붙입니다. 서버에는 원문 링크가 아니라 **해시만** 남습니다
(`TeamInvite`) — 다시 보여 줄 수 없으니 화면은 만들 때 **딱 한 번** 보여 주고, 다 쓴 뒤엔
"새 초대"를 쓰게 합니다. 예전 재입장 코드와 같은 타협입니다.

코드는 **아직도 받습니다.** 예전에 만들어진 팀이 `TeamInvite` 행이 없기 때문입니다
(`resolve-target.ts` 의 3번 길). 다만 `?t=` 초대 링크가 있으면 그 길로 **떨어지지 않습니다** —
초대는 명시적인 권한 증명이고, 그 증명이 실패했을 때 조용히 코드 길로 물러서면 증명의 실패가
숨겨집니다.

| 상황 | 흐름 |
|---|---|
| **처음 들어오기** | 이름·MBTI·희망 역할을 고르고 요청 → 팀장이 승인하면 자동으로 들어감 |
| **팀을 만든 첫 사람** | 승인해 줄 팀장이 없으므로 바로 들어가고, 그 사람이 팀장이 됨 |
| **재입장 (같은 이름, 새 기기)** | 아래 두 길 |
| **몇 팀에나 속해 있을 때** | 이메일 인증번호로 이 기기가 그 이메일의 소유자임을 증명하고, 그다음 고를 수 있는 팀을 고른다 |

이미 있는 이름으로 새 기기에서 들어오려면 둘 중 하나를 거칩니다.

| 길 | 언제 |
|---|---|
| **재입장 코드** | 첫 입장 때 한 번 보여 준 코드를 적는다. 서버에는 해시만 남는다 |
| **팀장 승인** | 코드가 없을 때. 팀장 화면에 요청이 뜨고 승인하면 저절로 들어간다 |

**이메일은 신원을 만들지 않습니다.** 인증번호를 통과하면 그 서버가 아는 사실은 "이 기기가
그 이메일의 소유자" 까지입니다. 권한은 그다음 `Member` 명단에서 나옵니다 — 이 이메일과
일치하는 팀원이 **있어야** 그 사람이 될 수 있고, 없으면 아무 팀에도 들어가지 못합니다.
증명이 담긴 쿠키는 `httpOnly` 이고 인증번호 수명(10분)만큼만 살아 있습니다.

발송은 **한 경로**입니다 — 환경변수에 따라 Gmail 또는 Resend 중 하나가 골라집니다. 발송이
실패하면 성공이라 하지 않습니다 — 형식적으로는 "보냈다"가 되지만 메일은 안 나간 상태라,
사용자는 받은 것처럼 기다리다 10분 뒤에야 만료됩니다. 운영에서는 발송이 실패했을 때 인증번호를
화면에 되돌려 주지도 않습니다(그 값이 새면 발송 경로가 우회됩니다). 로컬 개발에서만 서버 로그와
화면에 6자리가 함께 보입니다.

예전에는 **Supabase Auth 와 Resend 두 경로**를 병행했는데, 그 조합이 이 로그인을 고장 냈다.
같은 주소로 6자리가 **두 개** 나갔는데(Supabase 가 만든 것은 여기서 발급한 해시 토큰과
다른 코드였다) 어느 쪽인지 화면에 표시되지 않았고, 성공 판정은 "둘 다 실패했나"로 계산했는데
**Supabase 는 메일을 하나도 안 보내도 성공을 보고한다**(API 가 200 이었다는 뜻일 뿐이다).
그래서 `RESEND_API_KEY` 가 비어 있어 실제 메일이 0통이어도 "전송했습니다"가 되었다. 이 앱은
애초에 Supabase Auth 를 쓰지 않으므로(가입·로그인이 없는 제품이고 Supabase 는 파일 저장소
전용 — 2-1절) 발송자와 검증자를 각각 하나씩만 남겼다.

**팀장은 팀을 만든 사람**입니다(`Member.isLeader`). 만든 브라우저에 표시를 남겼다가
그 브라우저가 온보딩을 마칠 때 세웁니다.

같이 막은 것:

- **온보딩의 `upsert` 를 없앴습니다.** 예전에는 남의 이름을 적으면 기록을 이어받았고,
  그 과정에서 상대의 희망 역할·Veto 까지 덮어썼습니다 — 역할 추첨의 입력이 바뀌는 일입니다.
- **초대 코드를 6자리로** 늘렸습니다. 4자리는 32⁴ ≈ 105만이라 `/join?code=` 를 훑어
  실제 팀을 찾아낼 수 있었습니다. 6자리면 32⁶ ≈ 10억입니다.
- **세션이 서버에서도 만료됩니다**(90일). 쿠키 만료만 믿으면 쿠키 값을 한 번 얻은 쪽이
  영원히 씁니다.
- 재입장 코드를 연속으로 틀리면 10분 잠깁니다.

`/team/access` 에서 내 기기를 보고 내보낼 수 있고, 재입장 코드를 새로 받을 수 있습니다.

**팀장은 그냥 나갈 수 없습니다.** 팀장이 사라지면 새 기기 재입장을 승인해 줄 사람이 없어
팀원들이 기기를 바꾸는 순간 잠깁니다. 그래서 나갈 때 둘 중 하나를 골라야 합니다.

| 길 | 결과 |
|---|---|
| **팀장 넘기고 나가기** | 팀원 한 명을 골라 넘기고 나간다. 프로젝트는 그대로 |
| **프로젝트 없애기** | 팀이 통째로 사라진다. 되돌릴 수 없어 팀 이름을 직접 적어야 한다 |

넘기기만 하고 팀에 남을 수도 있습니다.

**나가도 `Member` 행은 지우지 않고 `leftAt` 만 찍습니다.** 기여 기록·메시지·파일 이력이
성적 근거라, 사람이 나갔다고 팀 기록에 구멍이 나면 안 됩니다. 명단과 집계에서만 빠지고,
같은 이름으로 다시 들어오면(재입장 문을 거쳐) 명단에 되돌아옵니다.

**추방은 두지 않습니다.** 팀에 있는 사람은 어차피 초대를 받아(링크든 코드든) 들어온 사람이고,
잘못 들어온 경우는 팀장이 재입장을 승인하지 않는 것으로 이미 막힙니다.

재입장 코드를 틀린 횟수는 **`RejoinAttempt` 표**에 셉니다(10분 창 안에 5회). 예전에는
프로세스 메모리의 `Map` 이었는데, 서버리스는 요청마다 다른 인스턴스가 받을 수 있어
인스턴스 수만큼 시도가 늘어났습니다 — 5회 제한이 사실상 없는 것과 같았습니다.
세는 키도 `초대 코드 + 이름`을 정규화해 해시한 값입니다(예전에는 사용자가 적은 문자열
그대로라 대소문자만 바꿔도 다른 칸으로 셌습니다).

### 2. AI 연결 (붙었음 — 남은 것은 운영)

도구 5종이 [`server/ai/tools.ts`](src/server/ai/tools.ts) 에서 OpenRouter 를 통해 지정된
모델을 부릅니다. 프롬프트가 곧 제품 약속이라 그 파일에 약속을 함께 적어 뒀습니다 — 쿠션 번역기가 마감을
늦춰 적거나 AI 서기가 정해지지 않은 담당자를 채우면 그건 버그입니다.

**리서처만 웹 검색을 붙였습니다.** "출처가 없는 결과는 보여주지 않는다"가 약속인데 검색
없이 물으면 있을 법한 논문 제목과 학회지 이름을 지어냅니다. 그래서 검색 결과에서 실제로
인용된 주소를 가진 카드만 남깁니다 — 프롬프트가 아니라 코드가 거릅니다.

**모델은 도구마다 다르게 고릅니다** — `OPENROUTER_MODEL_<도구>`(예: `OPENROUTER_MODEL_CLERK`).
없으면 `OPENROUTER_MODEL`, 그것도 없으면 `openrouter/free`(요청마다 다른 무료 모델)입니다.
고르는 자리는 [`server/ai/model.ts`](src/server/ai/model.ts) 의 `modelFor` 한 곳이고,
**모델 이름을 코드에 적지 않습니다** — 무료 카탈로그는 OpenRouter 가 돌려주고 며칠 지나면
바뀝니다(실측: 무료 모델 16개 전부 세대가 달랐고, 예전에 여기 적혀 있던 유료 슬러그는 목록에서
사라져 있었습니다).

**왜 도구마다 달라야 하는가 — 추측이 아니라 실측입니다.** `npm run tool:bench` /
`npm run cushion:bench` 로 같은 코퍼스를 나란히 돌린 결과(2026-09-30):

| 도구 | `inclusionai/ling-3.0-flash-sante:free` | `openrouter/free` |
|---|---|---|
| AI 서기 | **5/6** · 2.6초 | 3/6 · 22초 |
| 발표 지원 | **2/3** · 7초 | 2/3 · 10초 |
| AI 리서처 | **3/3** · 15초(출처 5개가 실제로 붙음) | **0/3** 전부 타임아웃 |
| 상황별 문장 | **3/3** · 2.5초 | 1/3 (없는 사실 "완료" 를 지어냄) |
| 쿠션 번역기 | **2/3** · 2.9초 | 2/3 (없는 약속 "천천히" 를 지어냄) |
| 읽기 순화 | ❌ **거절 16/26** | ✅ 거절 1/26 |

**읽기 순화만 예외입니다.** 구조화 출력을 잘하는 모델이 **심한 욕설을 순화하지 못하고 거절**합니다
— 순화가 가장 필요한 말에서 가장 자주 막히는 셈이라, 순화만 무료 라우터를 씁니다.
하나의 모델로 전부 잘 하는 것은 없습니다. 그래서 [`modelFor`](src/server/ai/model.ts) 가 있습니다.

> ⚠️ **이 슬러그들은 썩습니다.** 사라지면 404·429 가 납니다. 지금 쓸 수 있는 무료 모델과
> 함수 호출 지원 여부는 `npm run tool:bench -- --list-models` 로 확인하고,
> 위 표의 숫자를 다시 재려면 `npm run tool:bench -- --tool clerk --models <슬러그> --strict` 를
> 돌리세요. `--list-models` 의 표는 OpenRouter 의 **선언**이고 사실이 아닙니다 — 실측에서
> 그 16개 중 `tool_choice` 를 실제로 지킨 것은 3개뿐이었습니다.

**실패하면 한 번만 다시 부릅니다** — 다른 모델로(`OPENROUTER_FALLBACK_MODEL`, 없으면 무료
라우터). 일시적인 실패(타임아웃·연결 끊김·5xx·빈 응답)에만 합니다. **429 는 다시 시도하지
않습니다** — 몇 밀리초 뒤에 눌러도 똑같이 막히므로, 사용자에게 기다리라고 말하는 편이
정직합니다. 재시도는 모델 층에서 한 번에 끝납니다(`runTool` 이 아니라) — 그래야 한도도 한 번이고
"답을 받았거나 못 받았다" 는 둘뿐이라 위의 환불 규칙이 그대로 맞습니다.

- 요청마다 `AbortSignal` 로 끊습니다(`OPENROUTER_TIMEOUT_MS`, 기본 60초).
  SDK 의 `timeout` 만으로는 899초가 끊기지 않았습니다. **시간 초과는 일시적인 실패로 봅니다** —
  그 모델이 느렸다는 뜻이지 요청이 잘못됐다는 뜻이 아니므로, 다른 모델을 한 번 더 시도합니다.
- `tools.ts` 가 모델 출력을 그대로 믿지 않습니다. 그 규칙은
  [`lib/ai-draft-shape.ts`](src/lib/ai-draft-shape.ts) 로 **분리**했습니다 — "담당자 칸이 빈
  문자열로 왔다" 같은 걸러 내기는 **계약**이고, 계약은 스모크가 **모델을 부르지 않고** 확인해야
  합니다. 거기 두면 확인하려면 AI 를 불러야 하고, 그러면 안 지켜졌을 때 아무도 모릅니다.

품질이 필요하면 `OPENROUTER_MODEL_CLERK="anthropic/claude-sonnet-5"` 처럼 유료 슬러그로 바꾸세요.
**유료를 강제하지는 않습니다** — 지출은 사람이 정하는 값이고, 무엇을 썼는지는 계측이 남깁니다.

**하루 한도는 없습니다** (2026-09-28). 있었습니다 — 팀 200회 · 한 사람 60회, 읽기 순화는 따로
400 · 120. **그리고 14일간 한 번도 걸리지 않았습니다.** 운영 기록의 최고 하루가 도구 18회
(한도의 9%), 순화 1회였고, 거절된 날도 없었습니다. 무료 라우터가 속도 한도로 막은 적도
없었습니다(남은 실패는 안전 필터 거절 2건과 60초 타임아웃 1건 — 한도와 무관).

**근거 없는 숫자를 한도라고 부르지 않기로 했습니다.** 14일간 아무 일도 하지 않으면서
사용자에게 "하루 200회" 로 보이던 것은 한도가 아니라 거짓말이었습니다. 숫자 네 개를 지웠습니다.

남긴 것은 두 가지입니다 — **보관 기간 90일**과 **읽기 순화 폭주 차단**(하루 5,000, 사람 눈에
보이지 않음). 도구는 사람이 누릅니다. **읽기 순화만 메시지마다 자동으로** 도므로 여기만
무제한이 가능한 형태의 사고이고, 관측치의 5,000배인 숫자는 한도가 아니라 회로 차단기입니다.

- 세는 것은 **횟수뿐**입니다(`AiUsage`) — 입력한 글도 결과도 저장하지 않습니다.
  그 기록도 `AI_POLICY.retentionDays`(90일)가 지나면 예약 작업이 지웁니다.
  **이 기록은 지우지 않았습니다** — 오늘 "몇 번이나 쓰는가" 를 5분 만에 답한 것이 이 표였고,
  기록이 없으면 다음번에 같은 질문에 답할 수 없습니다.
- 키가 없어 **샘플이 나가는 호출은 기록하지 않습니다.** 모델을 부르지 않았으니까요.
- **모델이 실패한 호출은 기록에서 지웁니다.** 기록해 두고 시작하는데 되돌림이 없으면,
  무료 라우터가 자주 실패할수록 **한 번도 결과를 못 받은 실패**가 사용량으로 남습니다.
  우리가 정한 기록이 실패를 세면 그건 계측이 아니라 고지다.
  - 되돌림은 **아무 답도 못 받았을 때만** 일어납니다. 순화 폭주 차단(행을 만들지 않았음)과 모델
    거절(`throw` 가 아니라 돌려준 답)은 해당하지 않으므로, 안전 필터 거절이 공짜로 반복되는
    길은 열리지 않습니다.
  - **그 한 건만** 지웁니다(`AiUsage` 의 행 id 를 되돌려 받아서). 같은 날 같은 사람이 쓴 다른
    도구의 기록을 함께 지우는 사고를 막기 위함입니다.
- 도구 액션은 실패를 **던지지 않고 돌려줍니다**(`AiResult`). 운영 빌드의 Next 는 서버에서
  던진 오류 문구를 지우고 `digest` 만 보내서, 던지면 "한도를 다 썼습니다"가 사용자에게
  닿지 않습니다.
- 한도 수치 셋 다 **아직 확정되지 않은 값**입니다(`?review=1` 에서 허브의 `[검토]` 박스).

**두 개의 표가 있습니다 — 다릅니다.**

| 표 | 무슨 표인지 | 실패하면 |
|---|---|---|
| `AiUsage` | **몇 번 썼나**(기록, 한도 아님) | 행이 **사라집니다**(환불) |
| `AiCall` | **어떻게 됐나**(도구·모델·지연·결과) | **남습니다** |

한 표에 둘을 넣을 수 없어서 갈랐습니다. 환불 때문에 실패의 흔적이 지워지면 "이 도구가 왜
안 되나" 를 나중에 알 수 없기 때문입니다. `AiCall` 에도 **글은 남기지 않습니다** — 도구 ·
**실제로 응답한 모델** · 지연 · `ok`/`refused`/`failed` · 폴백 여부만 남깁니다
([`server/ai/call-stats.ts`](src/server/ai/call-stats.ts)).

- **`refused`(거절)는 `failed`(실패)와 다른 값**입니다. 거절은 **답이 온 것**입니다(모델이
  "못 하겠다"고 말했습니다). 한 값으로 합치면 "모델을 바꿔야 한다" 와 "다시 시도하면 된다" 가
  같은 0 으로 보입니다. 거부는 다시 눌러도 같습니다(실측 16/26).
- **재시도하면 `calls` 는 2 가 되고 한도는 1 입니다.** 비용과 지연은 2회분이라서 그래야 하고,
  `retried` 로 "폴백이 몇 번 먹혔나" 를 봅니다. 모델 층만 이 사실을 아는데, 호출 층이 판단하면
  재시도 경로 안에서 일어난 일이 통째로 사라집니다.
- 읽기 순화와 **형식이 같습니다** — 측정은 늘 두 군데를 오가서 봅니다.

**쿠션 번역기 · 문장 변환은 조각으로 옵니다** — "다듬는 중…" 만 4초간 도는 대신 글자가 조금씩
나옵니다. 서버 액션이 아니라 **Route Handler**([`app/api/ai/stream`](src/app/api/ai/stream/route.ts))를
씁니다 — 서버 액션으로 `ReadableStream` 을 돌려주는 방법은 **Next 문서에 없습니다**
(`node_modules/next/dist/docs/` 확인). Route Handler 의 스트리밍은 문서에 있고 버전 사이에
사라지지 않습니다.

- **이 길도 `runTool` 을 지납니다.** 한도·환불·출처 판정을 경로마다 따로 만들면 그 길에서만
  **조용히** 사라집니다(사용자는 "스트리밍이 안 돌아오네" 하고 그냥 기다립니다). 스트림의
  controller 를 `runTool` 밖에서 잡아 두고 `call` 안에서 조각을 밀어 넣는 이유는 **그대가
  유일하게 "답을 받았거나 못 받았다" 를 볼 수 있는 자리**이기 때문입니다. 스트리밍은
  **표현**의 문제지 **계약**의 문제가 아닙니다.
- **출처는 마지막 줄입니다.** 첫 조각과 함께 배지를 띄우고 싶지만 `ai` 인지 `sample` 인지를
  아는 곳은 `runTool` 하나뿐입니다. 여기서 `isAiConfigured()` 를 다시 부르면 그 판단이 두 곳에
  있고, 그랬을 때 바로 "예시가 AI 초안 배지 아래에 놓였다" 는 사고가 났습니다. 배지가 한 박자
  늦게 오는 것이, 글은 AI 냄새가 나는데 배지는 예시라고 나오는 것보다 낫습니다.
- **바이트를 글자로 되돌리는 자리만 따로 떼어[`lib/ai-stream-lines.ts`](src/lib/ai-stream-lines.ts)에
  두고 스모크가 확인합니다.** 한국어는 한 글자가 3바이트라, 바이트 경계에서 자르면 화면에 `�` 가
  납니다 — 사용자는 "모델이 이상한 글자를 냈다" 하고 오해합니다. 이 검사는 실제로 그 버그를
  잡아냈습니다(디코더를 매번 새로 만드는 구현이 통과하지 않는지까지 함께 봅니다).
- 예시는 **한 번에** 보냅니다. 예시를 조각으로 흉내 내면 "AI 가 쓰는 것처럼" 보이는데 실제로는
  모델이 한 일이 아닙니다.
- **이 두 도구의 서버 액션은 지웠습니다.** 화면이 옮겨 갔는데 액션을 남겨 두면 **아무도 부르지
  않는 모델 호출단**이 하나 더 남습니다 — 돈이 드는 죽은 코드입니다.


사용 내역은 CSV 로 내려받습니다 — `exportAiUsage()` 가 팀 전체 기록을 만들고, 화면이
`Blob` 으로 받아 파일로 저장합니다. 한도와 같은 기준(팀 단위, 한국 날짜)으로 세므로
내려받은 숫자가 화면의 숫자와 어긋나지 않습니다.

### 2-1. 홈 브리핑과 상황별 도구 추천

홈 맨 위에 **"오늘의 브리핑"** 카드가 있고, AI 도구 칩은 **규칙으로 고른 추천**으로 바뀝니다.
둘 다 [`features/home/briefing.ts`](src/features/home/briefing.ts) 에 있고, **모델을 부르지 않습니다.**

**브리핑이 세는 것은 다섯 개뿐이고, 나머지는 데이터가 없어서 세지 않습니다.**

| 세는 것 | 안 세는 것 | 이유 |
|---|---|---|
| ✅ 내 확인 대기 N건 | ❌ **회의가 끝났는데 메모 없음** | **회의록을 저장하는 곳이 없다** — 스키마에 모델이 없다 |
| ✅ 오늘 회의 | ❌ **발표 임박** | **발표일 필드가 없다.** `Team.dday` 는 "중간발표 D-12" 같은 문자열이다 |
| ✅ 마감을 아직 안 정한 일 N건 | | |
| ✅ **마감이 임박한 일 N건** | | |
| ✅ 남에게 알려 줄 일 N건 | | |

지워버린 게 아니라 **세지 않는다는 사실을 코드에 적어 뒀습니다.** 다음 사람이 "브리핑에 발표
임박도 넣자" 고 하면 그 이유가 바로 나옵니다.

⚠️ **"마감이 임박한 일" 은 `Task.dueAt`(2-0 절)이 생겨서 새로 늘어난 줄입니다.** 전에는
`Task.due` 가 자유 텍스트("9/19", "다음 주")라 비교할 시각이 없어서 **"아직 안 정했다"** 로
대체했습니다. 둘은 **다른 두 가지**입니다 — 하나는 사람이 비워 둔 것이고 다른 하나는 정했다가
다가온 것입니다. 한 줄로 합치면 그 줄은 아무것도 말하지 않게 되므로 **둘 다 셉니다.**

- ⚠️ **세는 것이 드뭅니다.** 기존 행은 백필하지 않았고 앞으로 사람이 **연도가 있는 값**을 적어야
  채워집니다. 그래도 괜찮습니다 — **있는 숫자만 말하는 것이 이 카드의 전부**이기 때문입니다.
- ⚠️ **표시 문자열을 여기서 다시 해석하지 않습니다.** `due` 를 브리핑에서 파싱하면 `lib/due.ts` 와
  **두 개의 기준**이 생기고 어느 쪽이 맞는지 알 수 없게 됩니다. 해석은 **한 곳에서만** 합니다.

- **마감 미정과 마감 임박은 따로 셉니다.** `dueOf` 가 빈 값을 `"미정"` 으로 저장하므로 그
  문자열은 **사람이 비워 뒀다** 는 뜻입니다. "다음 주" 같은 자유 텍스트는 **여전히 파싱하지
  않습니다** — 틀릴 확률이 높고, **틀린 숫자를 보여 주는 브리핑은 없는 것보다 나쁩니다.**
  정규값(`dueAt`)이 있을 때만 "임박" 을 세고, 없으면 **세지 않습니다.** 세는 것과 추측하는
  것을 구분합니다.
- **"마감이 없다" 고 말하지 않고 "아직 안 정했다" 고 말합니다.** 팀이 못 정한 것과 정하지
  않기로 한 것은 다릅니다.
- **`MeetingProposal.date` 가 `null` 이면 오늘 회의가 아닙니다.** 모르는 것과 아닌 것을
  같은 값으로 보면 "오늘 회의 없음" 이라는 거짓말이 됩니다.
- **"오늘" 은 서버가 정합니다.** 화면이 자기 시계로 맞추면 기기 설정이 다른 사람과 **같은
  홈이 다른 내용**을 보게 됩니다.
- **0 인 줄은 그리지 않습니다.** 할 일이 없는 팀에 빈 상자를 띄우면 그게 소음이고, 사용자는
  "앱이 뭔가 말 안 하네" 로 오해합니다. 빈 상태는 아래 "내 확인이 필요한 일" 의 패널이 이미
  하고 있습니다 — **두 곳에 "괜찮아요" 를 쓰지 않습니다.**

**추천 규칙은 세 개뿐이고, 전부 규칙입니다.**

1. 독촉할 일이 있으면 **쿠션 번역기** → poke 화면으로 바로 연결 (도구와 화면이 한 번에)
2. 발표 준비 제출함(`deck`·`script`) 마감이 3일 이내면 **발표 지원**
3. 자료 제출함(`research`) 마감이 3일 이내면 **AI 리서처**

- **AI 서기 추천은 없습니다.** 기획안의 규칙("회의가 끝났는데 메모가 없으면")은 **회의록을
  저장하는 곳이 없어** 판정할 수 없습니다. 지어내면 사용자는 "내 회의록이 사라졌다" 고
  오해합니다. 저장소가 생기면 그때 규칙 하나를 더합니다.
- **추천에 이유를 붙입니다.** 이유 없는 추천 칩은 광고이고, 한 번 눌러보고 "왜?" 하고 닫으면
  두 번째부터 보이지 않게 되어 추천의 값이 사라집니다.
- **추천이 없으면 원래 목록으로 되돌아갑니다.** 도구는 언제 쓸 수 있으므로 "지금은 아무 도구도
  필요 없다" 는 사실이 아니고, 빈 칩을 보여 주는 것은 도구 목록을 감춘 것입니다.
- **추천에서도 "다른" 규칙은 수학입니다.** "독촉할 일이 3건이다" 에서 "쿠션 번역기가 맞다" 까지
  논리가 없습니다. 틀리면 **한 번도 안 눌러본 도구**를 소개하는 셈이라 모델보다 규칙이 낫습니다.
- **"임박" 은 제출함 마감이지 팀 발표일이 아닙니다.** 팀 발표일 필드가 없어서 쓴 대체 근거가
  있는 값입니다. 브리핑 문구도 제출함이라고 적어 뒤집어쓰지 않습니다.

### 2-0. 업무 마감을 기계가 비교할 수 있게 (Task.due 정규화)

`Task.due` 는 **자유 텍스트**다. 실제로 `"9/19"`, `"9월쯤"`, `"다음 주"`, `"미정"`,
`"다음 발표까지"` 가 섞여 있어서 **"마감이 가까운 업무가 몇 건이냐" 를 셈으로 답할 수 없었다.**
그래서 브리핑은 그 자리를 "아직 안 정한 일" 로 대체했다 — 있는 숫자만 말하는 편이 나았다.

`SubmissionBox` 가 이미 `dueAt` + `due` 를 함께 들고 있어서 **같은 모양**을 tasks 에 더했다
([`lib/due.ts`](src/lib/due.ts) · 마이그레이션 `20261005090000_task_due_at`). 그리고 브리핑이
**"아직 안 정했다"** 로 대신하던 자리를 **"마감 임박"** 이라는 **자기 말로 되돌렸다**(2-1 절) —
두 값이 이제 나뉘었으므로요.

- **표시는 `due`, 비교는 `dueAt`.** 사람이 쓴 글은 그대로 보여 주고, 기계는 시각만 본다.
- ⚠️ **해석 못 하면 `null` 이고 그건 정상이다.** `2026-09-19` 처럼 **연도가 있는 값만**
  확실하다. `9/19` 는 **아직 지나가지 않은 해** 로 읽되, 어느 해가 의도인지 **모르면 `null`.**
- ⚠️ **기존 행은 백필하지 않는다.** 2025년에 쓴 "9/19" 가 2026년의 어느 날인지 **아무도 모른다.**
  추측해 채우면 그 값이 **근거 없는 사실**로 남고, 브리핑의 "마감 임박"이 그 위에서 선다.
  `null` 은 "모르겠다" 를 정직하게 말하는 값이다.
- **존재하지 않는 날을 거릅니다.** `new Date("2026-02-30")` 는 조용히 3월 2일이 되고,
  `2026-13-45` 는 `Invalid Date` 다. 둘 다 파싱에 넣으면 **틀린 마감**이 된다.
- **마감 문구를 고치면 정규값도 함께 고칩니다.** 빠뜨리면 사람이 고친 값과 화면이 말하는 값이
  어긋나 "마감이 3일 뒤" 가 거짓말이 된다. 그래서 **한 곳에서 둘을 같이 만듭니다.**
- 하루의 끝(23:59)으로 붙여 **"오늘 마감"** 을 말할 수 있게 했다 — `SubmissionBox` 와 같습니다.

**이제 브리핑이 "마감 임박" 을 셀 수 있습니다** — 정규값이 있는 일만. ⚠️ **세는 것이 드뭅니다.**
기존 행은 백필하지 않았고 앞으로 사람이 **연도가 있는 값**을 적어야 채워집니다. 드문 줄이어도
괜찮습니다 — **있는 숫자만 말하는 것이 이 카드의 전부**이기 때문입니다.

### 2-1-1. AI 도구 문맥과 담당자 매칭 (2단계)

AI 서기가 **우리 팀을 보고** 할 일 후보를 뽑습니다. DB 객체를 통째로 받는 것이 아니라
**허용된 필드만 골라 낸 문맥**을 넘깁니다
([`lib/team-tool-context.ts`](src/lib/team-tool-context.ts) · [`lib/tool-assignee.ts`](src/lib/tool-assignee.ts)).

- **허용 목록을 타입으로 고정했습니다.** 화면이 이미 갖고 있는 DTO 를 그대로 넣으면 안 쓰는
  값이 따라 나오고(기여 점수·MBTI·이메일), **내일 필드가 하나 추가되면 그것도 자동으로 나갑니다.**
  여기 없는 필드는 타입이 받지 않습니다 — 필드를 늘리려면 이 파일을 고쳐야 하고, 그 고침이
  검토 대상입니다.
- **넣지 않은 것: MBTI.** 프로젝트 원칙 — 역할 배정에 쓰지 않습니다. 문맥에 실려 있으면
  "비율에 맡기면 되겠다" 는 유속이 생기므로 **스모크가 부재까지 고정**합니다.
- **멤버 id 는 프롬프트에 넣지 않습니다.** 모델은 id 를 지어낼 뿐이라 **매칭은 코드가 합니다.**
- **나간 팀원은 명단에서 뺍니다** — 알림이 닿지 않으므로 담당자로 잡아도 아무도 모릅니다.

**담당자 매칭은 실패를 세 갈래로 구분합니다** — "안 됨" 하나로는 사람이 같은 실수를 되풀이합니다.

| 결과 | 뜻 |
|---|---|
| `matched` | 팀원 |
| `unset` | 모델도 정하지 않음 — 사람이 정하면 됨 |
| `no-match` | **명단에 없는 이름을 지웠습니다** — 화면이 이유를 말합니다 |
| `ambiguous` | **동명이인·같은 이름이 둘** — 아무나 고르면 아무도 책임질 사람이 없습니다 |

**한국어 이름의 두 형태를 다룹니다.** 명단은 `김민준` 인데 사람들은 `민준` 이라 말합니다.
완전 일치만 요구하면 정상 매칭의 대부분이 실패하므로 **성을 뗀 이름**을 허용하되, 겹치면
`null` 입니다. 그리고 **조사까지 떼어 냅니다** — 실측에서 모델이 `서연이` 로 적었고
(한 글자 차이라 `이서연` 과 매칭되지 않습니다), `민준이가` 처럼 **두 번** 떼어야 하는 경우도
있어서 반복 제거가 필요했습니다. **유사도 매칭은 하지 않는다** — `김민준경`·`민준씨` 는 그대로
실패한다. 매칭률을 올리면 틀린 배정이 같은 만큼 늘고, 팀플에서 담당자를 잘못 채우는 일은
그 일을 아무도 안 하게 만드는 일이다.

**비교 측정(N=4, 각 28회 호출, `ling-3.0-flash-sante:free`)**

| | 통과 |
|---|---|
| **명단 있음** | **28/28** |
| 명단 없음 | 14/28 |

명단이 없으면 **어떤 이름도 명단 형태로 나오지 않습니다** — 모델이 `민준·유나` 라고 적고
매칭은 `김민준·최유나` 를 찾습니다. 그래서 업무로 반영할 때 담당자가 거의 안 붙었습니다.

**⚠️ 단 한 번 돌린 결과는 측정이 아닙니다.** 무료 모델은 비결정적이라, 같은 설정·같은 코퍼스에서
`unnamed-1` 이 한 번은 `최유나`(실패)였고 한 번은 `null`(통과)였습니다. 그래서 벤치에
`--repeat` 를 넣었습니다. **"명단을 주니 담당자를 지어내는 모델" 이 있다는 우려는 실제로
재현했고**, 프롬프트에 "맡겠다는 말 없이 이름이 들어간 후보는 전부 버려라" 를 넣은 뒤 28/28 이
되었습니다 — 다만 강화 전 표본이 2회뿐이라 **인과는 확정하지 않았습니다.**

### 2-1-2. 서기 결과를 업무로 (2단계-a2)

**결정: 승인은 한 번 유지하되 담당자 칩의 출처를 밝힌다. 배정 알림은 보내지 않는다.**

- **배정 알림을 보내지 않는 이유** — 배정 상태를 만드는 것과 **그 사람에게 알림이 가게 하는
  것**은 다른 일입니다. 초안이 실제로 acknowledged 되면 사람이 고르지 않은 이름으로 상대방에게
  알림이 갑니다. `addTasksFromClerk` 는 `createMany` 라 지금 알림이 없는데, **그게 안전합니다.**
- **왜 출처를 밝히는가** — 담당자 칩은 **명단에 실제 있는 이름**을 보여 주므로 **결정한 것처럼
  읽힌다.** 스크롤만 하는 사람은 구분하지 못한다. 그래서 **단계를 늘리지 않고** 표시만 붙입니다:
  "메모에서 읽은 담당자예요".
- ⚠️ **사람이 그 칩을 건드리면 표시가 사라집니다.** 순환 버튼이라 **같은 이름으로 돌아올 수
  있는데**, 그때 값은 글자가 같아도 **누가 정했는지가 다릅니다.** 배정은 그대로 두고
  **표시만** 뺍니다 — 표시를 지우면 "AI 가 정했습니다" 는 사실이 되고 그건 이 저장소가 없애온 사고입니다.
- **담당자가 비면 아무것도 붙이지 않습니다.** `no-match`·`ambiguous` 안내가 이미 이유를 말합니다.
- **예시 결과에는 표시하지 않습니다.** 매칭을 시도하지 않았으므로 "AI 가 읽었다" 고 말할 수 없습니다.
- **매칭 규칙이 두 곳에 있으면 안 됩니다.** 서기 화면(후보 정리)과 업무 반영(`addTasksFromClerk`)
  이 같은 함수를 씁니다. 예전에는 업무 반영 쪽이 `roster.find(m => m.name === name)` 로
  **직접 정확 일치** 했고, 그래서 AI 서기가 `민준` 라고 적으면(명단은 `김민준`) **항상 담당자 없는
  업무가 생겼습니다.** 두 규칙이 갈라지면 "화면에서는 최유나 로 보이는데 업무에는 아무도 없다" 가
  조용히 벌어집니다.
- 매칭되지 않으면 그대로 **`null`** 입니다. **없는 사람에게 일을 배정하지 않습니다.**

### 2-1-3. 독촉과 검색에 팀 문맥 (2단계-b · c)

**poke(독촉) → 쿠션 번역기** — poke 화면에 "말투만 다듬고 보내기" 가 생깁니다
([`features/tasks/poke-request.ts`](src/features/tasks/poke-request.ts)). 별도 말은
**"진행상황 물어보기"와 요구하는 내용이 같습니다** — 달라지는 건 말투뿐입니다.

- ⚠️ **마감이 없으면 마감 문장을 만들지 않습니다.** `미정` 이면 "언제까지" 를 지어내지
  않습니다. 지어내면 독촉이 아니라 **압박**이고 그건 우리가 짊을 책임입니다.
- **업무 이름을 요약하지 않습니다.** "무엇을" 이 사라지면 독촉이 아니라 인상이 됩니다.
- **만들 수 없으면 `null`** 이고 버튼도 그리지 않습니다. 빈 문자열을 넘기면 쿠션 화면이 빈
  칸으로 열립니다.
- **오늘 이미 보낸 일은 다시 권하지 않습니다** — 같은 말을 두 번 다듬게 하면 한도가 두 번 깎입니다.
- 마감은 **자유 텍스트를 그대로 씁니다.** `Task.due` 정규화는 별도 트랙이고, 여기서 시각으로
  바꾸면 두 값이 어긋납니다("다음 주" 를 오늘로 읽으면 틀린 독촉이 됩니다).

**리서처 검색어 초안** — 팀 이름과 역할에서 후보를 뽑아 **칩으로 보여 줍니다**
([`features/tools/research-query.ts`](src/features/tools/research-query.ts)).

- ⚠️ **입력창을 자동으로 채우지 않습니다.** 리서처 결과는 그대로 주소로 쓰이므로 "왜 이
  결과가 나왔지" 를 물으면 **뭘 넣었는지가 답**입니다. 프로그램이 대신 정하면 그 답이 사라집니다.
  칩을 눌러 **넣기만 하고** 검색은 하지 않습니다 — 검색까지 하면 고르기 전에 결과가 화면을
  차지해 다른 후보를 못 봅니다.
- **업무 제목은 쓰지 않습니다.** 일마다 바뀌어 추천 목록이 매일 달라지고, "OO 정리" 를 그대로
  검색하면 이미 있는 글만 나옵니다. 바뀌는 목록은 신뢰를 떨어뜨립니다.
- 팀 이름에도 역할에도 값이 없으면 **빈 목록**입니다. "추천이 없습니다" 를 보여 주는 것은
  답이 없다는 뜻처럼 들립니다.
- 문맥 조회가 실패해도 **화면은 열립니다.** 검색어는 부가 기능이라 그 조회 때문에 리서처가
  막히면 "AI 가 고장났다" 고 오해하게 됩니다.

### 2-2. 파일 저장소

파일은 Supabase Storage 의 **비공개 버킷**(`submissions`)에 들어갑니다. 버킷은
`npm run db:storage` 로 한 번 만듭니다. 계약(2GB·버전·복원·멱등)은
[`npm run test:drive`](#드라이브-통합-검사) 가 지킨다.

이 앱은 **Supabase Auth 를 쓰지 않습니다.** 가입·로그인이 없는 제품이라 판단할 사용자가 없고,
Supabase 는 여기서 **파일 저장소 전용**입니다. 저장소 RLS 가 판단할 사용자를 만들지 않으므로
버킷을 비공개로 두고 **접근 권한은 앱이 서버에서 직접 확인합니다.**

그래서 **접근 권한은 앱이 서버에서 직접 확인하고**, 내려받기는 60초짜리 서명된 주소로만
내줍니다. 비밀 키(`SUPABASE_SECRET_KEY`)는 `server/storage/` 안에서만 쓰이고 브라우저로
나가지 않습니다 — 예전 이름인 `SUPABASE_SERVICE_ROLE_KEY` 도 받습니다.

- 한 파일 50MB, 문서·이미지·PPT·PDF 만 받습니다.
- 저장소 객체는 **버전마다 하나**입니다. 같은 경로에 덮어쓰면 옛 버전을 내려받을 때 새
  내용이 나와, 목록만 역사이고 내용은 하나인 가짜 버전 기록이 됩니다.
- 복원은 새 객체를 만들지 않고 **같은 객체를 가리키는 새 버전**을 더합니다.

**제출함 → 파일 목록 → 버전 기록**으로 한 단계가 늘었습니다. 핸드오프는 제출함에 파일이
하나뿐이라고 보고 곧장 버전 기록으로 들어갔는데, 실제로 올릴 수 있게 되면 한 제출함에
발표자료와 대본이 같이 들어갑니다.

### 2-3. 읽기 순화 (수신할 때 순화된 표현으로 보인다)

쿠션 번역기(15)는 **보내는 쪽**의 기능입니다 — 하고 싶은 말의 말투를 바꿔 보냅니다.
그게 전부였고, 받는 쪽에는 AI 가 손댈 게 없었습니다. 순화는 **`MessagePurification`** 에
**읽기 설정별로** 저장되고, 19 단톡방과 31 DM 에 도착한 남의 말은 다듬어져 보입니다.
원문(`Message.text`)은 **고치지 않습니다** — 순화는 보기에만 걸린다는 약속입니다.

## 무엇이 나가고, 무엇이 밖으로 나가나 — 읽기 순화의 경계

**곧장 말하겠습니다: 순화를 켜면 받는 쪽의 말이 OpenRouter 로 나갑니다.** 원문 그대로입니다.
사용자가 직접 입력한 것이니 "몰래 보내는 것" 은 아니지만, **보내지 않는다고 생각한 사람이
있을 수 있습니다.** 그래서 경계를 여기에 적습니다.

### 밖으로 나가는 것

- 순화 대상 말의 **본문** — AI 가 문장만 고치려면 원문이 필요합니다.
- 그 말의 **앞 2개 대화** — "누가 누구에게 무슨 말을 했는지" 를 알려면 앞뒤가 필요합니다.
- 읽는 사람의 **설정**(강도·말투) — "어떻게 읽어 달라" 라는 지시입니다.
  덩어리째 실리지는 않지만 그 값은 나갑니다.

### 밖으로 나가지 **않는** 것

- **보내는 사람 이름·이메일·비밀번호** — `packPurifyItems` 는 그 말을 AI 입력에 넣지 않습니다.
- **전체 대화 기록** — 앞 2개까지만, 그리고 그 두 개도 **읽을 대상이 아니라고 지시**합니다.
- **원문** — AI 가 본 것도 원문이고, 저장된 것도 순화본입니다. `Message.text` 는 안 바뀝니다.

### 왜 앞 2개인가 — 그리고 그 대가

앞말을 주지 않으면 순화가 **"이게 뭐야"** 를 모른 채 돌아갑니다. 한국어 욕설은 앞뒤로
읽어야 잡히는 것이 많습니다. 그래서 앞 2개를 줍니다.

대가는 **값이 하나 더 나간다**는 것입니다. 그래서 **정확히 2개로 고정**합니다. "이 방의
최근 N 말" 을 주면 같은 말을 읽는 사람마다 결과가 달라져 순화본 공유가 깨지기 때문입니다.
같은 말은 어디서 읽든 **같은 입력을 갖고, 그래서 순화는 결정함수이고 캐시가 맞습니다.**

꺼두는 방법은 한 곳이다 — `ReadCushion.enabled = false`. 그러면 **후보를 아예 만들지 않으므로
AI 호출이 0회**입니다. 끄고 읽는 동안 쌓인 순화본은 화면에 나오지 않습니다(지문이 달라
조회가 되지 않습니다).

**남아 있는 한계**: 사용자는 "이 말이 어디로 가나" 를 앱 안에서 볼 수 없습니다. AI 사용
내역(`/api/ai/usage`)에는 **몇 회 불렀나** 만 있고 **무엇을 보냈나** 는 없습니다. 그 사실을
화면에 넣는 것은 다음 일입니다.

## 파이프라인

```
메시지 도착
   └─ 대상 판정 (남의 말 · 글 있음 · 아직 상태 없음)
        └─ 선점(PENDING + claimToken)  ← 두 탭 경합 방지
             └─ 묶음(최대 10개) AI 1회  ← 한도 1회
                  ├─ 항목별 검사 통과 → PURIFIED   (라벨: 순화됨)
                  └─ 거절·검사 실패 → 규칙 가림 → FALLBACK (라벨: 공격적 표현 가림)
                       └─ 가릴 것도 없으면 REJECTED / FAILED → **원문**
   └─ 말풍선: 누르면 원문으로 돌아간다
```

`lib/read-cushion.ts` 가 이 계약 전체를 정하고 **화면과 서버가 같은 함수를 씁니다.**

## 왜 이렇게 복잡해졌나 — 실측

`openrouter/free` 로 **다툰 말**을 순화시키며 측정한 결과:

| 계층 | 결과 |
|---|---|
| 협조적 | 3/3 성공 |
| 짜증만 · 비꼼 · 탓 | 2~3/3 (실패 시 빈 응답) |
| 욕설("씨발·좀비") | 2/3, **욕을 남긴 채 통과** |
| 심한 욕설 | **0/3** — `User Safety: unsafe (Profanity, Harassment)` 명시적 거절 |

거절하지 않는 무료 모델을 직접 골라도(`nemotron`, `laguna`) **2/2 응답은 했지만 욕은
남았습니다** — "좀비처럼 달려가지 말고" → "좀비처럼 너무 빠르게 달려가지 말고". 프롬프트가
아니라 모델 능력의 한계이고, 이 표를 알아야 유료 모델 도입을 판단할 수 있다.

거절당하면 원문이 그대로 보이는 구조는 **이 기능이 가장 필요할 때 꺼지는 것**이라 그대로
둘 수 없었다. 그래서 두 갈래를 붙였다.

- **결정론적 가림(`FALLBACK`)** — AI 없이 **위험 표현 그 자리만** 가린다. 100% 동작하고 비용이
  없다. 단어를 지우면 문장이 깨진다(실측: "다 니 탓인데" → "인데") 그래서 **지우지 않고
  대체**한다. 그리고 **AI 결과인 투를 하지 않는다** — 라벨이 다르다(`공격적 표현 가림`).
- **상태 머신** — 성공·실패를 **같은 표에** 남긴다. 예전에는 "행이 없다 = 아직 안 함" 이라
  **거절된 말이 3초마다 다시 AI 후보**가 되었고, 새로고침하면 브라우저 메모리의 "시도함"
  기록까지 리셋되어 **하루 60회가 몇 분 만에 Gone** 이 되었다.

## 읽는 강도 3단계와 끄기

`ReadCushion` 은 **사람 × 방**마다 한 줄이고, 세 가지를 갖는다.

| 칸 | 뜻 |
|---|---|
| `enabled` | 끄면 **AI 호출 후보를 아예 만들지 않는다.** 원문으로만 읽는다. |
| `mode` | `LIGHT`(욕설만) · `NORMAL`(비꼼· 탓까지) · `STRONG`(책임 추굴까지) |
| `tone` | 같은 단계 안에서의 말투(15 쿠션 번역기와 같은 세 값) |

**끄기와 단계는 한 칸이 아니라 둘이다.** 한 칸(`mode: "OFF"`)으로 합치면 **끄기 전에 고른 단계를
잃는다** — 다시 켰을 때 어디까지 세게 읽을지 몰라 처음부터 골라야 한다. 대화를 잠깐 원문으로
읽다가 **내 자리로 돌아오는** 길이 있어야 한다.

**단계는 세 곳을 바꾼다** — 모델에게 줄 지시, 결과를 버리는 기준, 규칙 가림의 범위. 이 셋은
`lib/read-cushion.ts` 의 `LEVEL_PROFILES` **한 표**에서 나온다. 하나만 바꾸면 "약하게 순화하라
고 했는데 검사는 엄격하게 한다" 같은 어긋남이 생기고 어느 쪽이 문제인지 알 수 없다.
단계가 바뀌면 **읽는 지문이 달라진다** — "강하게" 를 골랐는데 "보통" 으로 만든 말을 보여주면
아무도 그 차이를 알 수 없다. 그래서 조회는 **지금 지문으로만** 일어나고, 새 지문에 아직
순화본이 없는 말은 `PENDING` 으로 보인다(다음 부름에서 그 지문으로 만들어진다).

예전에는 지우기까지 했다. 지금은 **지우지 않는다** — 순화본이 설정별로 저장되므로 옛 결과는
옛 설정으로 읽는 사람을 위해 남아 있고, **되돌릴 때 AI 0회**로 되기 때문이다.

**알려진 한계**: "니가 왜 그랬어요" 처럼 **대명사만 남은** 탓은 패턴으로 잡히지 않는다.
"니가" 를 낱말로 막으면 정상적인 요청("니가 알아서 해 줘")까지 걸리고, "왜" 로 막으면 "왜 이렇게
됐어요?" 라는 정당한 질문까지 버려진다. 그래서 하지 않았다 — 검사가 말을 막는 쪽이 더 나쁘다.
G 단계의 회귀 코퍼스로 실제 사례를 모은 뒤 판단한다.

## 지표 — 모델을 고르는 판단은 숫자로

이 기능은 느낌으로 튜닝하면 안 됩니다. 이미 실측으로 "협조적인 말은 되고 싸운 말은 안 된다" 가
나왔으므로, 뒤집는 근거는 숫자여야 합니다.

`server/ai/purify-stats.ts` 가 하루치를 집계하고 **예약 작업(`/api/cron/meetings`)이 로그와
응답에 남깁니다.** 화면은 만들지 않았습니다 — 판단에 필요한 숫자가 있으면 됩니다.

| 숫자 | 뜻 |
|---|---|
| `rows` | 순화 대상 말의 수(= 상태가 저장된 행) |
| `coverage` | 읽는 사람이 **끊김 없이** 읽을 수 있는 비율(순화 + 가림) |
| `aiShare` | 그중 **AI 가 실제로 한** 비율 |
| `buckets` | 순화됨 · 가림 · 거절 · 버림 · 실패 · 처리 중 |
| `reasons` | 어느 검사·어느 모델 탓인지 |
| `calls` / `avgLatencyMs` | 실제 AI 호출 수와 지연(행 기준 평균이라 큰 묶음에 끌림) |
| `modes` | 강도별 몇 명인지 |

**커버리지와 AI 비율을 따로 봐야 한다.** 실측 16말에서 커버리지는 81% 였지만 AI 비율은 69% 였다 —
**규칙 가림이 기능 전체를 버티고 있었다.** 커버리지만 높으면 기능은 돌아가는 것이고, AI 비율이
낮으면 모델을 바꿀 이유가 있다.

**토큰 수는 세지 않는다.** 무료 라우터에서는 비용이 아니라 품질·지연이 판단 기준이고, usage 를
올리기 위해 호출 한 겹을 더 밟는 것은 지금 값보다 비싸다.

## 모델 비교 — provider 계층과 회귀 코퍼스

"유료 모델로 바꾸면 되나" 는 **느낌으로 답할 수 없다.** 그래서 부르는 자리를 하나만 남기고
(`server/ai/cushion-provider.ts` 의 `purify` 한 개), **어느 모델로 부르는지만 바꾼다.** 화면·액션·
계약은 손대지 않는다.

**회귀 코퍼스**([`scripts/cushion-corpus.mts`](scripts/cushion-corpus.mts))가 기준이다. 순화본
문장을 그대로 적지 않고 **성질**만 약속한다 — `keep`(반드시 살아남아야 할 요구·마감·시각)과
`drop`(이 단계에서 반드시 없어야 할 것). 그 사이 말투는 자유라서 모델이 바뀌어도 코퍼스는 산다.

```bash
npm run cushion:bench -- --models openrouter/free,anthropic/claude-sonnet-5
npm run cushion:bench -- --models openrouter/free --level STRONG --strict
```

재는 것: `거절` · `유효`(검사 통과) · `욕설 잔존` · `의미 손실` · `말당 초`.
**욕설 잔존이 0 이 아니면 유효 수치를 믿으면 안 된다**(검사를 뚫었다는 뜻).

코퍼스는 **모델 없이 검사할 수 있는 세 가지를 `smoke.mts` 가 고정한다** — 원문은 검사를 통과하면
안 된다(그렇지 않으면 "순화됨" 라벨이 욕설에 붙는다), 깨끗한 말은 버리면 안 된다, 약속한 낱말만
가린다. 코퍼스는 실제로 이 자리에서 **구멍 2개를 찾았다**: 실측에서 살아남았던 "너 때문에" 가
목록에 없었고, "한심해" 가 `한심한|한심하` 패턴에 빠져 있었다(검사는 버리는데 가림이 통과).

### 다른 다섯 도구도 같은 방식으로 잰다

읽기 순화만 벤치가 있었고, 그래서 **서기·발표·리서처·쿠션·문장 변환은 눈으로만 확인했다** —
"방금 고친 게 나아졌다" 는 기억이 쌓이는 자리다. 같은 형식으로 전부 잰다
([`scripts/tool-corpus.mts`](scripts/tool-corpus.mts) · [`scripts/tool-bench.mts`](scripts/tool-bench.mts)).

```bash
npm run tool:bench -- --list                 # 도구별 코퍼스 크기
npm run tool:bench -- --list-models          # 지금 쓸 수 있는 무료 모델 · 함수 호출 지원 여부
npm run tool:bench -- --check-env            # .env 의 모델 슬러그가 카탈로그에 여전히 존재하는지
npm run tool:bench -- --tool clerk   --models openrouter/free --repeat 3 --compare
npm run tool:bench -- --tool research --models openrouter/free --strict
```

**세 도구가 어기는 약속이 다르므로 한 점수로 줄이지 않습니다.** 도구마다 자기 열이 있습니다 —
서기의 `담당자`(미정인 메모에 이름을 채웠나) · 발표의 `수치`(대본에 없던 수치를 넣었나) ·
리서처의 `지어냄`(인용되지 않은 주소) · 쿠션의 `요구`(말투만 바꾸다가 요구가 사라졌나).

> 이 벤치를 만들면서 **판정의 오류를 두 개 찾았습니다.** 하나는 후보 **제목만** 보고 "수치가
> 사라졌다" 고 판해 날짜(`due` 필드)를 놓친 것, 다른 하나는 프레임워크가 아니라 **모델이
> 틀렸다고 착각할 뻔한 것**입니다. 판정이 틀리면 그 위에서 모델을 고르게 되므로, 고치는 쪽이
> 모델을 고르는 쪽보다 먼저입니다.

`--strict` 는 계약을 어긴 모델에서 종료 코드가 1이 됩니다(정렬용 · CI 아님 — 모델을 부르므로
`npm test` 에는 들어가지 않습니다). **비용 없이 검사할 수 있는 불변식은 `smoke.mts` 가 합니다** —
담당자 `null` 을 코드에서 거르는 규칙, 재시도해도 되는 실패의 종류, 여섯 도구의 라우팅이
env 를 어떻게 읽는지 같은 것들입니다.

### 실측(같은 코퍼스, `openrouter/free`, 26개 말)

| 회차 | 거절 | 유효 | 욕설 잔존 | 의미 손실 | 말당 초 |
|---|---|---|---|---|---|
| 1 | 16/26 | 1/26 | 0 | 0 | 11.5 |
| 2 | 9/26 | 14/26 | 0 | 1 | 22.9 |

**같은 코퍼스인데 회차마다 하늘과 땅이다** — 무료 라우터가 요청마다 무작위 모델을 고르기
때문이다. 거절(빈 응답·60초 타임아웃)이 회차에 따라 35%~62%. 이것이 유료 모델을 "기다리는" 것이
아니라 **측정해야 결정할 수 있는 것**이라는 뜻이다.

## 재호출을 막는 계약

| 상태 | 언제 다시 부르나 |
|---|---|
| `PURIFIED` / `FALLBACK` | **끝.** 다시 부르면 읽고 있던 말이 조용히 바뀐다. |
| `PENDING` | 선점 유효 시간(90초) 안이면 안 붙는다. 시간이 지나면 **사라진 요청**이므로 가져갈 수 있다. |
| `REJECTED` / `FAILED` | **같은 설정으로는 안 부른다.** `model` 이나 `promptVersion` 이 바뀌었거나, 백오프가 지나고 시도 횟수가 남았을 때만. |

`attemptCount` · `retryAfter` · `sourceHash` · `model` · `promptVersion` · `validatorVersion` 을
남기는 이유가 이것입니다. 프롬프트를 고쳤을 때 **무엇을 다시 만들어야 하는지** 판단하려면
"이건 어느 조건에서 왜 실패했는가" 가 있어야 합니다.

## 항목별 계약 (배열 순서가 아니라 id)

요청은 `{"task":…,"items":[{"id","text"}]}` 이고 응답은 `{"items":[{"id","text"}]}` 다.
- **순서가 바뀌어도, 하나가 빠져도** 요청한 id 의 결과만 받아옵니다. 10개 중 8개 성공이면
  8개는 순화되고 2개만 원문으로 남습니다 — 예전처럼 **묶음 전체를 버리지 않습니다.**
- **본문을 데이터로 보냅니다**(`items[].text`). 글로 붙이면 "이전 지시를 무시해" 같은 문장이
  **지시로 읽힐 수 있습니다.**
- 항목마다 두 단계로 검사합니다: **구조**(id 존재·중복·빈 글·길이) → **의미·안전**(욕설 제거,
  **정보 보존**, 길이 폭주). "민수가 API 배포 오늘까지 한다" → "조금 더 신경 써주세요" 는
  공격성은 0 이지만 **정보가 죽었으니** 버립니다(`INFO_LOST`).

실측(4개 묶음, 실제 모델): 3개 `PURIFIED`, 욕설이 있던 1개는 `TOXICITY_REMAINED` 로 버려진 뒤
**규칙 가림으로 이어받았습니다.** 같은 4개를 다시 요청하자 **0초·AI 0회** 로 저장된 상태가
돌아왔습니다.

### 3. 확정한 정책과 남은 것

`?review=1` 로 켜면 화면 안 `[검토]` 박스가 모두 보입니다. 서버를 붙이기 전에 정해야
한다고 적어 두었던 세 가지는 **모두 정했습니다**(하나는 팀이 고르는 값으로 바뀌었고, 하나는
입구까지 만들었습니다).

- **몇 명이 확인해야 기록이 확정되는지 — 팀이 고릅니다.** 1명이 기본이고(전원으로 두면 한
  사람이 답하지 않을 때 영영 확정되지 않습니다), **팀장만** 17 화면에서 바꿀 수 있습니다
  (`Team.confirmsNeeded`). 기준을 올리면 팀의 기록을 전부 다시 계산합니다 — 1명 확인이었던
  기록이 "확정"이라면 그 말 자체가 거짓이기 때문입니다. 바꾸기 전에 **몇 건이 다시 기다리게
  되는지 말하고 한 번 더 받습니다.** 올릴 수 있는 최댓값은 팀원 수에서 자기 기록의 주인을
  뺀 만큼이고(자기 기록은 자기 자신이 확인하지 못합니다), 서버가 그 이상을 거절합니다.
  모인 확인은 지워지지 않습니다 — 기준에 다시 도달하면 그대로 확정돼요.
- **누가 정정에 응답할 수 있는지 — 기록 주인과 그 의견을 적은 사람.** 결론을 적는 자리는
  다툼의 당사자 몫입니다. 17 화면은 남은 팀원에게 버튼 대신 **왜 없는지도 같이 말하고**,
  서버도 같은 조건을 다시 봅니다(`canResolveContrib`) — 주소를 알면 화면을 거치지 않고
  들어올 수 있기 때문입니다.
- **답이 없으면 어떻게 되나 — 세 번째 길로 닫습니다.** 닫는 방법은 "정정 의견에 동의" ·
  "공동 작업으로 나눔" · **"합의 없음 · 원문 유지"** 셋입니다(23 화면). 셋째가 없으면
  답하지 않은 의견이 영영 닫히지 않아 팀이 문서를 낼 수 없었습니다. 닫으면 기록은
  `pending` 으로 돌아가고 확인 절차가 다시 돕니다 — **확정은 아닙니다.**
  - 한쪽 말로 덮지 않는다는 원칙은 그대로입니다: 양쪽 의견이 이력에 남고, 리포트는 닫혔지만
    답이 없는 것을 **"정리되지 않은 의견 N건"** 으로 셉니다. 지우면 "아무도 이의가 없었다"고
    읽히는 문서가 됩니다.
  - **반한 사람은 그 기록을 확인하지 못합니다** — 자기 반대를 스스로 동의로 바꾸는 셈이라
    막습니다(`canConfirm` 한 함수를 화면과 서버가 함께 씁니다). 17 화면은 버튼을 감추고
    **왜인지도 같이 말합니다.**
  - 화면은 결론의 **키**를 보내고 서버가 문구를 만듭니다. 예전에는 문자열이 무엇이든
    저장돼서, 집계가 한국어 문장을 읽어야 했습니다.
  - **시간 자동 마감을 두지 않았습니다** — 자동 상태 변경은 경계하는 쪽이고(마감 계산조차
    화면에서 계산합니다), 반대한 사람의 말을 시스템이 대신 정리할 이유가 없습니다.
- **회의 참여는 팀장이 직접 표시합니다.** 앱이 입장·발언·시간을 정확히 아는 쪽이 아니라
  자동 판정이 정직하지 않다는 판단입니다. **17 화면(팀원 확인)에만** 입구를 두었습니다 —
  거기가 "기록이 사실인가"를 판단하는 자리라서입니다. 정한 뒤로:
  - **기록 하나**에 붙습니다. 참여자를 따로 적지 않습니다 — `record.memberId` 가 곧 참여자라
    두 곳에 적으면 서로 어긋납니다. 공동 작업은 23 화면의 정정 응답("공동 작업으로 나눔")이 그
    자리를 이미 맡고 있습니다.
  - **지워도 흔적이 남습니다.** 취소는 표시를 없애지 않고 "누가 · 언제 취소했는지"를 남깁니다
    (`ContribParticipation`). 공로 평가가 아니라 사실 기록이라 조작이 드러나야 나중에 따져
    볼 수 있고, "왜 참여 표시가 있나"에 답할 수 있어야 합니다. 한 기록에 표시가 두 개일 수는
    없습니다 — 유일 인덱스가 막습니다(`MeetingProposal.activeKey` 와 같은 방식).
  - **확인과 독립입니다.** 참여한다고 기록이 확정되지 않습니다. 의견 차이가 떠 있어도 찍을
    수 있게 뒀습니다 — 다툼은 기록의 *내용*에 대한 것이고 사람이 그 일을 했는지는 별개다.
  - **자기 기록에도** 팀장이 찍을 수 있습니다. 확인(맞습니다)은 "기록이 사실인가"를 남이
    판단하는 것이고, 참여 표시는 팀장이 정하는 자리이기 때문입니다.
  - 18 리포트에는 사람별 **"참여 표시 N건"** 이 1건 이상일 때만 나옵니다. 정렬도 강조도 하지
    않습니다 — 이 리포트의 첫 원칙이 "점수·순위를 만들지 않는다"이기 때문입니다.

**아직 정하지 않은 것은 문서에 적지 않습니다.** 원본은 화면 안에 있는 `[검토]`(`Undecided`) 상자이고, `npm run decisions` 가 코드를 훑어 그 목록을 읽습니다 — 지금 24건입니다. 그 상자를 고쳐야 목록이 고쳐지므로, 문서에 손으로 적은 목록은 어느 순간 코드와 어긋납니다(핸드오프 정책표가 정확히 그렇게 됐고 "AI 사용량 한도 없음" 이 한참을 거짓말이었습니다).

무엇을 먼저 정할지는 `npm run decisions` 스크립트 머리말의 우선순위 세 가지가 말합니다.
어느 화면에 붙은 항목인지는 `?review=1` 로 그 화면을 열면 점선 상자로 그대로 보입니다.

- **읽기 순화의 강도**(2-2) — `LIGHT/NORMAL/STRONG` 3단계이고, 끄는 것은
  별도(`OFF` 가 아니라 읽기 순화 설정의 켜기·끄기)입니다. 단계는 **모델에게 주는 지시·결과를
  버리는 기준·AI 가 거절했을 때 규칙으로 가리는 범위** 를 **한 표**에서 나옵니다
  ([`lib/read-cushion.ts`](src/lib/read-cushion.ts) 의 `LEVEL_PROFILES`) — 셋을 따로 두면
  "약하게 순화하라 고 했는데 검사는 강하게 한다" 는 어긋남이 조용히 생깁니다. 단계 수와
  이름은 기획안에 없어 세 단계로 두었습니다(15 번 말투와 같은 사정).
- **읽기 순화의 AI 몫은 따로 센다**(2026-09-28). 순화는 누가 누를 때만 일어나지 않고
  **대화방을 열면 알아서** 돌기 때문에, 같은 장부를 썼을 때 실제로 일어난 일은 한 사람이
  대화방을 많이 여는 것만으로 팀의 쿠션 번역기·리서처 몫이 바닥나고 화면이 "AI 한도를 다
  썼습니다" 라고 말하는 것이었습니다. 이제 **따로** 세고(`AI_POLICY.readCushion*`), 도구
  몫(팀 200 · 1인 60회)에서는 순화를 **빼고** 셉니다 — 두 번 차감하지 않게 하는 게 요점입니다.
  기록은 여전히 `AiUsage` 한 표에 함께 남습니다.
  **수치는 400·120 이고, 같은 날 무료 라우터(`openrouter/free`)로 확정**했습니다. 처음의
  150·40 은 유료 슬러그를 전제한 값이었고 근거가 바뀌었으므로 올렸습니다. 놓치지 않으려고
  [`AI_POLICY`](src/data/catalog.ts) 주석에 **왜 이 값인지, 무엇이 바뀌면 다시 내려야
  하는지**를 적어 두었습니다 — 실사용량과 모델을 다시 볼 때 거기서 근거를 읽으면 됩니다.
  **한도가 막혀도 규칙 가림이 그대로 적용되므로 안전 구멍은 아닙니다**(`server/actions/chat.ts`
  의 묶음 실패 경로가 거절과 같은 `maskRiskyParts` 를 쓴다). 잃는 것은 **덜 다듬어진 말**이고,
  그 수준은 사용자가 고른 강도에 따라 정해집니다. 무료 라우터의 실측상 심한 욕설에서는
  모델이 0/3 으로 거절하므로, 한도까지 조이면 이 기능이 사실상 빨간 칠 도구가 됩니다.

### 4. 아직 손대지 않은 것
