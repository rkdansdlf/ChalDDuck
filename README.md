# 찰떡 (ChalDduck)

대학생 팀 프로젝트(팀플)를 위한 협업 앱. 가입·로그인 없이 **초대 코드 + 이름**으로 들어와서
역할을 조율하고, 회의 시간을 잡고, 자료를 모으고, 기여 기록을 남깁니다.

디자인 핸드오프(33화면 프로토타입)를 실제 코드베이스로 옮기는 중입니다.

## 스택

| | |
|---|---|
| 프레임워크 | Next.js 16 (App Router) · React 19 · TypeScript |
| 스타일 | Tailwind CSS v4 + CSS 변수 디자인 토큰 |
| 아이콘 | lucide-react (직접 등록한 것만 번들에 들어감) |
| 서체 | Pretendard Variable (저장소에 포함, `next/font/local`) |
| 데이터 | PostgreSQL (Supabase) + Prisma |
| AI | OpenRouter (기본 `openrouter/free`) |
| 서버 | Next.js Server Actions |

### 처음 실행

```bash
npm install
```

`.env` 를 만들고 Supabase 대시보드 > Connect 의 값으로 채웁니다
(`.env.example` 참고 — 커밋되지 않습니다).

#### 로컬 DB 로 개발하기 (권장)

`.env` 는 **운영(배포본)과 같은 Supabase** 를 가리킵니다. 개발 중에 누르는 버튼이
실제 팀의 데이터를 바꾸지 않도록, 로컬 Postgres 를 따로 두고 `.env.development.local` 로
덮어씁니다(커밋되지 않습니다).

```bash
createdb chalddeok_dev               # Homebrew Postgres 기준
```

```bash
# .env.development.local
DATABASE_URL="postgresql://<사용자>@localhost:5432/chalddeok_dev"
DIRECT_URL="postgresql://<사용자>@localhost:5432/chalddeok_dev"
SUPABASE_URL=""                      # 파일 저장소를 끈다 — 운영 버킷에 쌓이지 않게
```

```bash
npx prisma migrate deploy            # 표 만들기
npm run db:seed                      # 데모 팀 한 개 넣기
npm run dev
```

이 파일은 `next dev` 뿐 아니라 **Prisma CLI 와 시드도 먼저 읽습니다**
([`scripts/load-env.mjs`](scripts/load-env.mjs)). 그래서 파일이 있는 동안에는
`prisma migrate` 가 운영 DB 로 가지 않습니다. 운영에 직접 마이그레이션해야 할 때만
잠시 치우세요(평소에는 배포가 `prisma migrate deploy` 를 돌립니다).

시드는 로컬이 아닌 DB 를 가리키면 멈춥니다(같은 초대 코드의 팀을 지우고 다시 넣기
때문입니다). 정말 원격에 넣으려면 `ALLOW_REMOTE_SEED=1` 을 붙입니다.

로컬 시드에는 데모 팀원 네 명이 같은 재입장 코드를 받습니다 — `/join/rejoin` 에서
초대 코드 `CD3-7F2Q`, 이름(김민준·이서연·박지호·최유나), 재입장 코드 `DEMO-DEMO-DEMO`.
원격에 넣을 때는 코드를 넣지 않습니다(누구나 아는 코드는 뒷문이 됩니다).

`DATABASE_URL` 은 런타임용 **트랜잭션 풀러(6543)**, `DIRECT_URL` 은 마이그레이션·시드용
**직결(5432)** 입니다. 풀러로는 prepared statement 와 DDL 잠금을 못 버텨 마이그레이션이 깨집니다.

런타임 커넥션 풀은 [`src/server/db.ts`](src/server/db.ts) 에서 직접 만듭니다 — 쉬고 있던
연결이 끊겼을 때 프로세스가 죽지 않게 받아 주고, 순간적인 연결 실패(P1001·P2024)는
짧게 두 번 다시 시도합니다. 자세한 이유는 그 파일 주석에 있습니다.

## 구조

```
src/
  app/                  라우트
    join/               01 초대 링크 입장 · 00 팀 만들기 · 이메일 로그인

    (tabs)/             하단 5탭(홈·채팅·일정·드라이브·팀)이 붙는 화면들
  components/ui/        공통 컴포넌트 (핸드오프 ui.jsx 대응)
  features/             화면 코드 — chat · contrib · drive · home · onboarding ·
                        roles · schedule · social · tasks · team · tools
  server/               서버에서만 도는 코드 — DB 연결·세션·쓰기 액션과
                        AI·인증·푸시·레이트리밌·파일 저장소
  data/                 읽기 전용 조회(api.ts) · 제품 설정값(catalog.ts)
  lib/                  도메인 타입·MBTI·유틸
```

**이 블록은 파일을 다 적은 게 아닙니다.** 어느 폴더에 무엇이 들어 있는지 알려 주기 위한
간단한 안내입니다. 화면 번호(07·11·13 등)와의 대응은 [`docs/handoff/HANDOFF.md`](docs/handoff/HANDOFF.md)
에 있고, 새 폴더를 만들면 굳이 여기를 고칠 필요가 없습니다.

## 반응형

| 폭 | 레이아웃 |
|---|---|
| ~599px | 뷰포트를 꽉 채우고 **하단 5탭**으로 이동 |
| 600~1023px | 본문이 860px 까지만 넓어지고 가운데 정렬 · 하단 탭바 유지 |
| 1024px~ | 탭바가 **왼쪽 세로 막대**로 바뀌고 본문에 폭을 내줌 |

폭이 생기면 화면도 그에 맞게 바뀝니다 — 홈은 두 기둥, 드라이브 제출함은 두 줄,
기여도 리포트는 A4 비율, 08 시간표 격자는 칸이 44px 로 커져 최소 탭 영역을 지킵니다.

온보딩은 탭이 없는 집중 흐름이라 넓은 화면에서도 420px 카드로 모읍니다 —
입력칸 하나가 화면 폭만큼 늘어나면 읽기 어렵습니다.

**채팅(33번)은 넓은 화면에서 실제로 3분할로 동작합니다.**

| 폭 | 채팅 |
|---|---|
| ~1023px | 화면을 한 번에 하나씩 (32 → 19 / 31) |
| 1024px~ | 목록 + 대화 |
| 1280px~ | 목록 + 대화 + 자료·정보 |

1024px 에서 세 기둥을 다 펴지 않는 이유는 왼쪽 앱 내비게이션이 232px 을 이미 쓰기 때문입니다 —
거기서 세 기둥을 펴면 대화 칸이 말풍선 한 줄도 못 담습니다.


## 검토 모드

기획안에 규칙이 없어 임시로 정한 지점은 화면 안에 `[검토]` 점선 박스로 표시돼 있고,
**평소에는 보이지 않습니다.** 확인하려면 URL 에 `?review=1` 을 붙이거나 콘솔에서 `__CD_REVIEW__()`.

확정이 필요한 지점의 목록은 **여기에 적지 않습니다** — 화면이 곧 목록이고, 위의 방법으로
한 번에 다 볼 수 있습니다. 문서에 개수를 적어 두면 화면이 늘었는데 숫자를 고치지 않는 일이
반복됩니다. 원래 기획안과 주고받은 기록은 [`docs/handoff/HANDOFF.md`](docs/handoff/HANDOFF.md)
에 남아 있습니다(역사 문서이므로 지금의 목록과 다를 수 있습니다).

## 검사

```bash
npm run verify
```

`db:check` 는 **지금 가리키는 DB** 와 스키마를 비교합니다. 로컬에서 돌리면 로컬 DB(에셋)를
봅니다 — "마이그레이션을 깜빡했나"를 잡는 검사입니다. **"운영 DB 가 뒤처졌나"를 잡는
것은 Vercel 빌드 쪽** `db:check` 입니다(거기서는 `DIRECT_URL` 이 운영 DB 를 가리킵니다).
두 개를 같은 이름으로 부르는 이유가 있어 헷갈리기 쉬우니 기억해 두세요.

## 배포 (Vercel)

**배포돼 있습니다 — https://chalddeok-omega.vercel.app**

저장소가 Vercel 프로젝트(`chalddeok`)에 연결돼 있어 `main` 에 푸시하면 자동으로 배포됩니다.
**배포는 항상 푸시한 커밋에서** 일어납니다 — Vercel 이 `github.com/rkdansdlf/ChalDDuck` 를
그 커밋으로 클론해서 빌드합니다.

`npx vercel --prod` 로 직접 올릴 수도 있지만 그러면 **푸시하지 않은 커밋까지 배포**됩니다.
배포본이 `main` 보다 앞서고, 다음 푸시가 또 다른 배포를 만들어 배포 이력이 두 갈래로
벌어집니다. 되도록 푸시로만 올리세요.

`vercel.json` 의 `buildCommand` 가 빌드 순서를 정합니다 —
`prisma migrate deploy && npm run db:check && next build`. **푸시 = 마이그레이션 적용 +
가드 + 빌드** 이므로 `db:check` 를 빠뜨릴 길이 없습니다.

새로 세팅한다면 저장소를 Vercel 프로젝트에 연결하고 **환경변수 여덟 개**를 넣으면 됩니다.

| 변수 | 없으면 |
|---|---|
| `DATABASE_URL` | 앱이 뜨지 않습니다 (런타임 · 트랜잭션 풀러 6543) |
| `DIRECT_URL` | **빌드가 실패합니다** — 마이그레이션이 이걸 씁니다 (직결 5432) |
| `CRON_SECRET` | 회의 마감 예약 작업이 항상 401 입니다 |
| `SUPABASE_URL` + `SUPABASE_SECRET_KEY` | 파일 업로드만 막히고 앱은 돕니다 |
| `OPENROUTER_KEY` | AI 도구가 샘플만 돌려주고 앱은 돕니다 |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` + `VAPID_PRIVATE_KEY` | **푸시가 전혀 나가지 않습니다** — 알림함의 "알림 받기"가 켜지지 않는다고 그대로 말합니다 |
| `RESEND_API_KEY` | **이메일 로그인이 되지 않습니다** — 발송 실패라고 그대로 말합니다 |
| `NEXT_PUBLIC_APP_URL` | 도착한 메일의 매직 링크가 `http://localhost:3000` 을 가리켜 링크를 눌러도 로그인이 되지 않습니다 |

`RESEND_API_KEY` 와 `NEXT_PUBLIC_APP_URL` 은 이메일 로그인(`19 단톡방` 외 모든 입구의 보조
경로)에만 쓰입니다. 없는 동안에도 나머지 앱은 그대로 돕습니다 — 다만 **운영에서 인증번호를
화면에 되돌려 주는 도움은 꺼집니다.** 그 값이 새면 메일 발송이 실패해도 인증번호가 도착해
로그인 경로가 우회되기 때문입니다. 로컬 개발(`next dev`)에서만 6자리가 서버 로그와 화면에
보입니다.

푸시 키 쌍은 `npx web-push generate-vapid-keys` 로 한 번만 만듭니다. **배포와 로컬에
같은 값**을 넣어야 합니다 — 서버와 브라우저의 키가 다르면 구독은 만들어지지만 아무것도
오지 않습니다(화면은 "켜짐"이라고 말합니다). 값을 바꾸면 예전에 구독한 기기들이 전부
구독을 다시 해야 합니다.

⚠️ **`.env` 는 배포본과 같은 Supabase 프로젝트입니다.** `.env.development.local` 없이
`npm run dev` 를 띄우면 로컬에서 누른 것이 그대로 실제 팀의 데이터가 됩니다 — 위의
"로컬 DB 로 개발하기"를 먼저 해 두세요.

빌드 명령은 `vercel.json` 에 있습니다 —
`prisma migrate deploy && npm run db:check && next build`.
**배포할 때마다 마이그레이션이 먼저 돕고, 그다음 DB 가 스키마와 같은지 확인합니다.**

#### `db:check` — 왜 있는가

`prisma migrate deploy` 는 **"할 일이 없다"를 실패로 보지 않습니다.** 그래서
`prisma/schema.prisma` 만 고치고 마이그레이션 파일을 빠뜨려도 배포가 **초록불**입니다.
그렇게 올라간 Prisma 클라이언트는 첫 질의에서 죽고, 죽은 건 서버 컴포넌트라
브라우저에는 `Minified React error #441` 로만 찍힙니다. 실제로 그렇게 배포가 성공하고
`/chat` 이 깨진 적이 있습니다 — 서버 컴포넌트가 예외를 내면 RSC 페이로드의 에러 행으로
바뀌고, 그 행을 클라이언트가 되살린 것이 441 입니다. **진짜 원인은 Vercel 함수
로그에만 있습니다.**

그래서 마이그레이션을 덮은 **직후에** DB 와 스키마를 직접 비교합니다
(`prisma migrate diff`, [`scripts/check-schema-in-sync.mjs`](scripts/check-schema-in-sync.mjs)).
차이가 있으면 **빌드가 실패합니다.** 로컬에서 미리 확인하려면 `npm run db:check`.

규칙 하나만 지키면 됩니다: **`prisma/schema.prisma` 를 건드린 커밋에는 반드시
마이그레이션을 함께 넣는다.** 그래야 `migrate deploy` 가 할 일을 찾습니다.

버킷은 한 번만 만들면 됩니다(`npm run db:storage`). **버킷은 Supabase 에만 있습니다** —
로컬 Postgres 에는 `storage` 스키마가 없어 이 명령이 목적을 이루지 못합니다. 그래서
로컬 DB 를 가리키면 아무것도 건드리지 않고 그 사실을 알려주고 끝냅니다.

예전에는 이 명령이 `.env`(운영)만 읽어, `next dev` 는 로컬 DB 를 보는데 **운영 DB 의 버킷을
바꾸러 갔습니다.** 시드가 가진 가드를 붙여 로컬이 아닌 곳을 가리키면 명시적 허락
(`ALLOW_REMOTE_SEED=1`) 없이는 실패하게 했습니다. 버킷을 만들 대상은 직접 지목하세요 —
운영에 만들려면 그쪽 주소를 담은 환경에서 실행하고 `ALLOW_REMOTE_SEED=1` 을 붙입니다.

⚠️ **Vercel Hobby 는 예약 작업이 하루 한 번까지**입니다. `vercel.json` 의 schedule 을
그보다 잦게 적으면 **배포가 실패합니다**. 지금은 하루 한 번(00:00 KST)이고, 화면이
`effectiveStage()` 로 직접 계산하므로 이 작업이 늦어도 사용자는 맞는 상태를 봅니다.

### 1-1. 회의 응답 마감

마감은 시각이 지나면 저절로 오는 일이라 아무도 앱을 열지 않아도 지나갑니다. 두 겹으로 둡니다.

- **표는 예약 작업이 맞춥니다.** `/api/cron/meetings` 를 주기적으로 부르면 마감이 지난 제안을
  `confirmed` 로 바꿉니다(`vercel.json` 에 **하루 한 번** 등록 — Vercel Hobby 는 그보다
  잦으면 배포가 실패합니다. Pro 이상이면 schedule 만 바꾸면 됩니다). 다른 데 올린다면 어떤
  스케줄러로든 이 주소만 부르면 됩니다. `CRON_SECRET` 이 없으면 **항상 401** 입니다.
  이 작업이 지난 재입장 시도 기록과 보관 기간이 지난 AI 사용 기록도 함께 치웁니다 —
  둘 다 하루 한 번이면 충분하고, 늦어도 틀리지는 않습니다.

마감이 지난 뒤의 반대는 서버가 거절합니다 — 받아 주면 이미 확정된 회의가 뒤집힙니다.
24시간을 기다리지 않고 마감 뒤 화면을 보려면 09 화면의 "마감 지금으로 당기기 (데모)"
버튼을 쓰세요(개발 환경에서만 보입니다). **확정하지 않고 시계만 당기므로** 그 버튼으로 본
화면이 실제 마감 뒤의 화면과 같습니다.

### 1-2. 인증

가입·로그인은 없습니다. 대신 **팀에 들어오는 모든 길의 마지막 문을 팀장이 엽니다.**
팀장이 초대 코드를 보냈든 본인이 요청했든 같습니다 — 코드가 한 번 새면 누구든 팀의
기여 기록과 대화를 볼 수 있기 때문입니다.

| 상황 | 흐름 |
|---|---|
| **처음 들어오기** | 이름·MBTI·희망 역할을 고르고 요청 → 팀장이 승인하면 자동으로 들어감 |
| **팀을 만든 첫 사람** | 승인해 줄 팀장이 없으므로 바로 들어가고, 그 사람이 팀장이 됨 |
| **재입장 (같은 이름, 새 기기)** | 아래 두 길 |

이미 있는 이름으로 새 기기에서 들어오려면 둘 중 하나를 거칩니다.

| 길 | 언제 |
|---|---|
| **재입장 코드** | 첫 입장 때 한 번 보여 준 코드를 적는다. 서버에는 해시만 남는다 |
| **팀장 승인** | 코드가 없을 때. 팀장 화면에 요청이 뜨고 승인하면 저절로 들어간다 |

**팀장은 팀을 만든 사람**입니다(`Member.isLeader`). 만든 브라우저에 표시를 남겼다가
그 브라우저가 온보딩을 마칠 때 세웁니다.

같이 막은 것:

- **온보딩의 `upsert` 를 없앴습니다.** 예전에는 남의 이름을 적으면 기록을 이어받았고,
  그 과정에서 상대의 희망 역할·Veto 까지 덮어썼습니다 — 역할 추첨의 입력이 바뀌는 일입니다.
- **초대 코드를 6자리로** 늘렸습니다. 4자리는 32⁴ ≈ 105만이라 `/join?code=` 를 훑어
  실제 팀을 찾아낼 수 있었습니다. 6자리면 32⁶ ≈ 10억입니다.
- **세션이 서버에서도 만료됩니다**(90일). 쿠키 만료만 믿으면 쿠키 값을 한 번 얻은 쪽이
  영원히 씁니다.
- 재입장 코드를 연속으로 틀리면 10분 잠깁니다.

`/team/access` 에서 내 기기를 보고 내보낼 수 있고, 재입장 코드를 새로 받을 수 있습니다.

**팀장은 그냥 나갈 수 없습니다.** 팀장이 사라지면 새 기기 재입장을 승인해 줄 사람이 없어
팀원들이 기기를 바꾸는 순간 잠깁니다. 그래서 나갈 때 둘 중 하나를 골라야 합니다.

| 길 | 결과 |
|---|---|
| **팀장 넘기고 나가기** | 팀원 한 명을 골라 넘기고 나간다. 프로젝트는 그대로 |
| **프로젝트 없애기** | 팀이 통째로 사라진다. 되돌릴 수 없어 팀 이름을 직접 적어야 한다 |

넘기기만 하고 팀에 남을 수도 있습니다.

**나가도 `Member` 행은 지우지 않고 `leftAt` 만 찍습니다.** 기여 기록·메시지·파일 이력이
성적 근거라, 사람이 나갔다고 팀 기록에 구멍이 나면 안 됩니다. 명단과 집계에서만 빠지고,
같은 이름으로 다시 들어오면(재입장 문을 거쳐) 명단에 되돌아옵니다.

**추방은 두지 않습니다.** 팀에 있는 사람은 어차피 초대 코드를 받아 들어온 사람이고,
잘못 들어온 경우는 팀장이 재입장을 승인하지 않는 것으로 이미 막힙니다.

재입장 코드를 틀린 횟수는 **`RejoinAttempt` 표**에 셉니다(10분 창 안에 5회). 예전에는
프로세스 메모리의 `Map` 이었는데, 서버리스는 요청마다 다른 인스턴스가 받을 수 있어
인스턴스 수만큼 시도가 늘어났습니다 — 5회 제한이 사실상 없는 것과 같았습니다.
세는 키도 `초대 코드 + 이름`을 정규화해 해시한 값입니다(예전에는 사용자가 적은 문자열
그대로라 대소문자만 바꿔도 다른 칸으로 셌습니다).

### 2. AI 연결 (붙었음 — 남은 것은 운영)

도구 5종이 [`server/ai/tools.ts`](src/server/ai/tools.ts) 에서 OpenRouter 를 통해 지정된
모델을 부릅니다. 프롬프트가 곧 제품 약속이라 그 파일에 약속을 함께 적어 뒀습니다 — 쿠션 번역기가 마감을
늦춰 적거나 AI 서기가 정해지지 않은 담당자를 채우면 그건 버그입니다.

**리서처만 웹 검색을 붙였습니다.** "출처가 없는 결과는 보여주지 않는다"가 약속인데 검색
없이 물으면 있을 법한 논문 제목과 학회지 이름을 지어냅니다. 그래서 검색 결과에서 실제로
인용된 주소를 가진 카드만 남깁니다 — 프롬프트가 아니라 코드가 거릅니다.

**모델은 `.env` 의 `OPENROUTER_MODEL` 로 고릅니다.** 기본값 `openrouter/free` 는 무료 모델
하나를 요청마다 무작위로 고르는 라우터입니다. 돈은 들지 않지만 **같은 요청이 899초(실패)·
5.3초·3.9초로 갈렸고**, 담당자 자리에 `null` 대신 빈 문자열을 넣는 등 지시를 덜 정확히
따릅니다. 그래서

- 요청마다 `AbortSignal` 로 60초에 끊습니다(`OPENROUTER_TIMEOUT_MS` 로 조절).
  SDK 의 `timeout` 만으로는 위의 899초가 끊기지 않았습니다.
- `tools.ts` 가 모델 출력을 그대로 믿지 않습니다 — 빈 담당자는 "미정"으로 돌리고,
  인용되지 않은 주소가 붙은 자료 카드는 버립니다.

품질이 필요하면 `OPENROUTER_MODEL="anthropic/claude-sonnet-5"` 처럼 유료 슬러그로 바꾸세요
(실측 3~6초, 5종 모두 규칙대로 동작 확인).

**하루 한도가 있습니다** — 팀 200회 · 한 사람 60회(한국 날짜 기준). 호출마다 돈이 들고
쿠션 번역기·문장 변환은 입력이 멎을 때마다 한 번씩 부르므로, 문이 "팀원인가" 하나뿐이면
비용에 바닥이 없습니다. 한도를 넘으면 화면이 그 사실을 그대로 말합니다.

- 세는 것은 **횟수뿐**입니다(`AiUsage`) — 입력한 글도 결과도 저장하지 않습니다.
  그 기록도 `AI_POLICY.retentionDays`(90일)가 지나면 예약 작업이 지웁니다.
- 키가 없어 **샘플이 나가는 호출은 한도에서 깎지 않습니다.** 모델을 부르지 않았으니까요.
- 도구 액션은 실패를 **던지지 않고 돌려줍니다**(`AiResult`). 운영 빌드의 Next 는 서버에서
  던진 오류 문구를 지우고 `digest` 만 보내서, 던지면 "한도를 다 썼습니다"가 사용자에게
  닿지 않습니다.
- 한도 수치 셋 다 **아직 확정되지 않은 값**입니다(`?review=1` 에서 허브의 `[검토]` 박스).

사용 내역은 CSV 로 내려받습니다 — `exportAiUsage()` 가 팀 전체 기록을 만들고, 화면이
`Blob` 으로 받아 파일로 저장합니다. 한도와 같은 기준(팀 단위, 한국 날짜)으로 세므로
내려받은 숫자가 화면의 숫자와 어긋나지 않습니다.

### 2-1. 파일 저장소

파일은 Supabase Storage 의 **비공개 버킷**(`submissions`)에 들어갑니다. 버킷은
`npm run db:storage` 로 한 번 만듭니다.

이 앱은 Supabase Auth 를 쓰지 않아(가입·로그인이 없는 제품입니다) 저장소 RLS 가 판단할
사용자가 없습니다. 그래서 **접근 권한은 앱이 서버에서 직접 확인하고**, 내려받기는 60초짜리
서명된 주소로만 내줍니다. 비밀 키(`SUPABASE_SECRET_KEY`)는 `server/storage/` 안에서만
쓰이고 브라우저로 나가지 않습니다 — 예전 이름인 `SUPABASE_SERVICE_ROLE_KEY` 도 받습니다.

- 한 파일 50MB, 문서·이미지·PPT·PDF 만 받습니다.
- 저장소 객체는 **버전마다 하나**입니다. 같은 경로에 덮어쓰면 옛 버전을 내려받을 때 새
  내용이 나와, 목록만 역사이고 내용은 하나인 가짜 버전 기록이 됩니다.
- 복원은 새 객체를 만들지 않고 **같은 객체를 가리키는 새 버전**을 더합니다.

**제출함 → 파일 목록 → 버전 기록**으로 한 단계가 늘었습니다. 핸드오프는 제출함에 파일이
하나뿐이라고 보고 곧장 버전 기록으로 들어갔는데, 실제로 올릴 수 있게 되면 한 제출함에
발표자료와 대본이 같이 들어갑니다.

### 2-2. 읽기 순화 (수신할 때 순화된 표현으로 보인다)

쿠션 번역기(15)는 **보내는 쪽**의 기능입니다 — 하고 싶은 말의 말투를 바꿔 보냅니다.
그게 전부였고, 받는 쪽에는 AI 가 손댈 게 없었습니다. 순화는 **`MessageCushion`** 에
사람·말 단위로 저장되고, 19 단톡방과 31 DM 에 도착한 남의 말은 다듬어져 보입니다.
원문(`Message.text`)은 **고치지 않습니다** — 순화는 보기에만 걸린다는 약속입니다.

## 파이프라인

```
메시지 도착
   └─ 대상 판정 (남의 말 · 글 있음 · 아직 상태 없음)
        └─ 선점(PENDING + claimToken)  ← 두 탭 경합 방지
             └─ 묶음(최대 10개) AI 1회  ← 한도 1회
                  ├─ 항목별 검사 통과 → PURIFIED   (라벨: 순화됨)
                  └─ 거절·검사 실패 → 규칙 가림 → FALLBACK (라벨: 공격적 표현 가림)
                       └─ 가릴 것도 없으면 REJECTED / FAILED → **원문**
   └─ 말풍선: 누르면 원문으로 돌아간다
```

`lib/read-cushion.ts` 가 이 계약 전체를 정하고 **화면과 서버가 같은 함수를 씁니다.**

## 왜 이렇게 복잡해졌나 — 실측

`openrouter/free` 로 **다툰 말**을 순화시키며 측정한 결과:

| 계층 | 결과 |
|---|---|
| 협조적 | 3/3 성공 |
| 짜증만 · 비꼼 · 탓 | 2~3/3 (실패 시 빈 응답) |
| 욕설("씨발·좀비") | 2/3, **욕을 남긴 채 통과** |
| 심한 욕설 | **0/3** — `User Safety: unsafe (Profanity, Harassment)` 명시적 거절 |

거절하지 않는 무료 모델을 직접 골라도(`nemotron`, `laguna`) **2/2 응답은 했지만 욕은
남았습니다** — "좀비처럼 달려가지 말고" → "좀비처럼 너무 빠르게 달려가지 말고". 프롬프트가
아니라 모델 능력의 한계이고, 이 표를 알아야 유료 모델 도입을 판단할 수 있다.

거절당하면 원문이 그대로 보이는 구조는 **이 기능이 가장 필요할 때 꺼지는 것**이라 그대로
둘 수 없었다. 그래서 두 갈래를 붙였다.

- **결정론적 가림(`FALLBACK`)** — AI 없이 **위험 표현 그 자리만** 가린다. 100% 동작하고 비용이
  없다. 단어를 지우면 문장이 깨진다(실측: "다 니 탓인데" → "인데") 그래서 **지우지 않고
  대체**한다. 그리고 **AI 결과인 투를 하지 않는다** — 라벨이 다르다(`공격적 표현 가림`).
- **상태 머신** — 성공·실패를 **같은 표에** 남긴다. 예전에는 "행이 없다 = 아직 안 함" 이라
  **거절된 말이 3초마다 다시 AI 후보**가 되었고, 새로고침하면 브라우저 메모리의 "시도함"
  기록까지 리셋되어 **하루 60회가 몇 분 만에 Gone** 이 되었다.

## 재호출을 막는 계약

| 상태 | 언제 다시 부르나 |
|---|---|
| `PURIFIED` / `FALLBACK` | **끝.** 다시 부르면 읽고 있던 말이 조용히 바뀐다. |
| `PENDING` | 선점 유효 시간(90초) 안이면 안 붙는다. 시간이 지나면 **사라진 요청**이므로 가져갈 수 있다. |
| `REJECTED` / `FAILED` | **같은 설정으로는 안 부른다.** `model` 이나 `promptVersion` 이 바뀌었거나, 백오프가 지나고 시도 횟수가 남았을 때만. |

`attemptCount` · `retryAfter` · `sourceHash` · `model` · `promptVersion` · `validatorVersion` 을
남기는 이유가 이것입니다. 프롬프트를 고쳤을 때 **무엇을 다시 만들어야 하는지** 판단하려면
"이건 어느 조건에서 왜 실패했는가" 가 있어야 합니다.

## 항목별 계약 (배열 순서가 아니라 id)

요청은 `{"task":…,"items":[{"id","text"}]}` 이고 응답은 `{"items":[{"id","text"}]}` 다.
- **순서가 바뀌어도, 하나가 빠져도** 요청한 id 의 결과만 받아옵니다. 10개 중 8개 성공이면
  8개는 순화되고 2개만 원문으로 남습니다 — 예전처럼 **묶음 전체를 버리지 않습니다.**
- **본문을 데이터로 보냅니다**(`items[].text`). 글로 붙이면 "이전 지시를 무시해" 같은 문장이
  **지시로 읽힐 수 있습니다.**
- 항목마다 두 단계로 검사합니다: **구조**(id 존재·중복·빈 글·길이) → **의미·안전**(욕설 제거,
  **정보 보존**, 길이 폭주). "민수가 API 배포 오늘까지 한다" → "조금 더 신경 써주세요" 는
  공격성은 0 이지만 **정보가 죽었으니** 버립니다(`INFO_LOST`).

실측(4개 묶음, 실제 모델): 3개 `PURIFIED`, 욕설이 있던 1개는 `TOXICITY_REMAINED` 로 버려진 뒤
**규칙 가림으로 이어받았습니다.** 같은 4개를 다시 요청하자 **0초·AI 0회** 로 저장된 상태가
돌아왔습니다.

### 3. 확정한 정책과 남은 것

`?review=1` 로 켜면 화면 안 `[검토]` 박스가 모두 보입니다. 서버를 붙이기 전에 정해야
한다고 적어 두었던 세 가지는 **모두 정했습니다**(하나는 팀이 고르는 값으로 바뀌었고, 하나는
입구까지 만들었습니다).

- **몇 명이 확인해야 기록이 확정되는지 — 팀이 고릅니다.** 1명이 기본이고(전원으로 두면 한
  사람이 답하지 않을 때 영영 확정되지 않습니다), **팀장만** 17 화면에서 바꿀 수 있습니다
  (`Team.confirmsNeeded`). 기준을 올리면 팀의 기록을 전부 다시 계산합니다 — 1명 확인이었던
  기록이 "확정"이라면 그 말 자체가 거짓이기 때문입니다. 바꾸기 전에 **몇 건이 다시 기다리게
  되는지 말하고 한 번 더 받습니다.** 올릴 수 있는 최댓값은 팀원 수에서 자기 기록의 주인을
  뺀 만큼이고(자기 기록은 자기 자신이 확인하지 못합니다), 서버가 그 이상을 거절합니다.
  모인 확인은 지워지지 않습니다 — 기준에 다시 도달하면 그대로 확정돼요.
- **누가 정정에 응답할 수 있는지 — 기록 주인과 그 의견을 적은 사람.** 결론을 적는 자리는
  다툼의 당사자 몫입니다. 17 화면은 남은 팀원에게 버튼 대신 **왜 없는지도 같이 말하고**,
  서버도 같은 조건을 다시 봅니다(`canResolveContrib`) — 주소를 알면 화면을 거치지 않고
  들어올 수 있기 때문입니다.
- **답이 없으면 어떻게 되나 — 세 번째 길로 닫습니다.** 닫는 방법은 "정정 의견에 동의" ·
  "공동 작업으로 나눔" · **"합의 없음 · 원문 유지"** 셋입니다(23 화면). 셋째가 없으면
  답하지 않은 의견이 영영 닫히지 않아 팀이 문서를 낼 수 없었습니다. 닫으면 기록은
  `pending` 으로 돌아가고 확인 절차가 다시 돕니다 — **확정은 아닙니다.**
  - 한쪽 말로 덮지 않는다는 원칙은 그대로입니다: 양쪽 의견이 이력에 남고, 리포트는 닫혔지만
    답이 없는 것을 **"정리되지 않은 의견 N건"** 으로 셉니다. 지우면 "아무도 이의가 없었다"고
    읽히는 문서가 됩니다.
  - **반한 사람은 그 기록을 확인하지 못합니다** — 자기 반대를 스스로 동의로 바꾸는 셈이라
    막습니다(`canConfirm` 한 함수를 화면과 서버가 함께 씁니다). 17 화면은 버튼을 감추고
    **왜인지도 같이 말합니다.**
  - 화면은 결론의 **키**를 보내고 서버가 문구를 만듭니다. 예전에는 문자열이 무엇이든
    저장돼서, 집계가 한국어 문장을 읽어야 했습니다.
  - **시간 자동 마감을 두지 않았습니다** — 자동 상태 변경은 경계하는 쪽이고(마감 계산조차
    화면에서 계산합니다), 반대한 사람의 말을 시스템이 대신 정리할 이유가 없습니다.
- **회의 참여는 팀장이 직접 표시합니다.** 앱이 입장·발언·시간을 정확히 아는 쪽이 아니라
  자동 판정이 정직하지 않다는 판단입니다. **17 화면(팀원 확인)에만** 입구를 두었습니다 —
  거기가 "기록이 사실인가"를 판단하는 자리라서입니다. 정한 뒤로:
  - **기록 하나**에 붙습니다. 참여자를 따로 적지 않습니다 — `record.memberId` 가 곧 참여자라
    두 곳에 적으면 서로 어긋납니다. 공동 작업은 23 화면의 정정 응답("공동 작업으로 나눔")이 그
    자리를 이미 맡고 있습니다.
  - **지워도 흔적이 남습니다.** 취소는 표시를 없애지 않고 "누가 · 언제 취소했는지"를 남깁니다
    (`ContribParticipation`). 공로 평가가 아니라 사실 기록이라 조작이 드러나야 나중에 따져
    볼 수 있고, "왜 참여 표시가 있나"에 답할 수 있어야 합니다. 한 기록에 표시가 두 개일 수는
    없습니다 — 유일 인덱스가 막습니다(`MeetingProposal.activeKey` 와 같은 방식).
  - **확인과 독립입니다.** 참여한다고 기록이 확정되지 않습니다. 의견 차이가 떠 있어도 찍을
    수 있게 뒀습니다 — 다툼은 기록의 *내용*에 대한 것이고 사람이 그 일을 했는지는 별개다.
  - **자기 기록에도** 팀장이 찍을 수 있습니다. 확인(맞습니다)은 "기록이 사실인가"를 남이
    판단하는 것이고, 참여 표시는 팀장이 정하는 자리이기 때문입니다.
  - 18 리포트에는 사람별 **"참여 표시 N건"** 이 1건 이상일 때만 나옵니다. 정렬도 강조도 하지
    않습니다 — 이 리포트의 첫 원칙이 "점수·순위를 만들지 않는다"이기 때문입니다.

여전히 정하지 않은 것:

- 의견 차이가 끝까지 안 좁혀졌을 때의 최종 기재 방식. 지금은 양쪽 의견을 함께 남깁니다.
- **반대를 철회하는 길**은 없습니다 — 직접 쓴 의견은 기록에 그대로 남습니다. 사후에
  "내가 그랬던 것 같다"로 바꾸려면 기록 주인과 다시 적어야 합니다.
- **읽기 순화의 강도**(2-2). 지금은 보내는 쪽(15)과 같은 세 말투를 빌려 씁니다 — 읽을 때는
  "분명하게" 가 낯설 수 있습니다. `OFF/LIGHT/NORMAL/STRONG` 같은 강도 단계, 규칙 가림의 범위,
  그리고 읽기 순화에 AI 몫을 따로 둘지가 모두 미정입니다.
- **읽기 순화에 AI 몫을 따로 둘지.** 지금은 15번과 같은 하루 한도(팀 200 · 1인 60회)를
  씁니다. 순화가 언제나 돌면 읽는 것만으로 그 몫을 쓰므로, 보내는 쪽의 쿠션 번역기를 못 쓰는
  상황이 생길 수
  있어 별도 예산이 나을 수 있습니다 — 값은 정해지지 않았습니다.

### 4. 아직 손대지 않은 것

- (없습니다) — 회의 참여 표시는 17 화면에 붙었습니다(3절). 앱 안 알림함이 있는 자리에
  **휴대폰 푸시 알림**을 붙였습니다. 알림함의 "알림 받기"로 켜면 앱을 닫아 둔 사이 오는 일이
  기기로 닿고, 켤 수 없는 기기(아이폰의 설치 전, 서버 키 없음)는 **그 사실을 말하고** 버튼을
  막습니다. 푸시 키를 Vercel 에 넣지 않은 동안에는 켜지지 않습니다(위 표 참고).

무엇이 이미 끝났는지는 각 절의 말로 알 수 있습니다 — 메시지 첨부(2-1 참고), 쿠션 번역기
→ 단톡방 전송(`viaCushion` 표시와 함께), 읽기 순화(2-2), AI 사용 내역 내려받기는 모두
붙어 있습니다.
